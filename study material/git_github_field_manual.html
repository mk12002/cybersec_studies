01 — Foundations

Why version control exists

Every version control system is an answer to one question: when several people change the same set of files over time, how do you reconstruct any past state, understand who changed what, and combine two sets of changes without losing either?

Before you learn commands, understand the three architectures, because Git's design decisions only make sense as reactions to what came before.

The three generations

What a VCS must give you

ReconstructionRestore the exact state of the whole project at any past point, not just one file.
AttributionWho changed which line, when, and with what stated reason. The foundation of code review and of most audit evidence.
ConcurrencyTwo people editing the same tree simultaneously, with a defined procedure for combining results.
IsolationWork in progress that does not destabilise what everyone else is building on. This is what branches are for.
IntegrityDetection of accidental corruption and of deliberate tampering. Git does the first well and the second only partially.
Frame this security-first

Version control is a system of record for the code that becomes production. That makes it three things at once: an integrity control, an audit trail, and a very attractive target. If an attacker can write to your default branch, they do not need a production exploit. They will be deployed by your own pipeline, with your own signatures, through your own change process. Hold that thought through every section.

02 — Foundations

Git is not GitHub

Conflating the two is the single most common source of confused security thinking. They have different trust models, different failure modes and different controls.

DimensionGitGitHub / GitLab / Bitbucket
What it isAn open-source, local program that manages a content-addressed object database in a .git directory.A hosted product built around Git, adding identity, permissions, review, automation and a web UI.
Created2005, by Linus Torvalds, after BitKeeper's free licence was withdrawn from the Linux kernel project.2008 as GitHub; acquired by Microsoft in 2018.
IdentityNone. user.name and user.email are arbitrary local strings.Real accounts, MFA, SSO, tokens, audit logs, org membership.
AuthorizationWhatever the filesystem and transport allow.Roles, teams, branch protection, rulesets, CODEOWNERS, environments.
Code reviewNot a concept. git request-pull just formats an email.Pull requests, required approvals, required checks, merge queues.
AutomationLocal hooks only, and they do not travel with a clone.Actions / Pipelines: server-side CI/CD with secrets and cloud credentials.
Attack surfaceParser bugs, hook execution, protocol handling, local credential files.Account takeover, token theft, workflow injection, third-party apps, fork abuse.
If it disappearsNothing. It is on every machine.You keep the code and lose issues, PR discussion, CI history, releases and permissions.

The practical consequence is this: almost every control you actually rely on lives on the platform, not in Git. Git will happily let anyone write any history under any name. Branch protection, required reviews, signature verification and audit logs are all things GitHub enforces at push time. A repository moved off the platform, or accessed by a path that bypasses the platform, loses all of them at once.

Threat — the bypass path

Controls enforced at the platform's front door do not apply to side doors. Watch for self-hosted mirrors that push to production, deploy keys with write access that sidestep branch protection, admins with bypass permissions on rulesets, and CI service accounts excluded from required reviews "because the bot needs to push". Each one reintroduces raw Git into a workflow that was supposed to be governed.

03 — Internals

The object database

Git is a content-addressed key-value store with a version control user interface bolted on. Learn the store and every command stops being magic.

There are exactly four object types. Every one of them is stored the same way: zlib-compress a header plus a payload, hash the uncompressed bytes, and file the result under that hash. The hash is the name. Identical content anywhere in history is stored once.

blobRaw file content. No filename, no permissions, no timestamp. Just bytes.
treeA directory listing. Entries of mode · type · hash · name, pointing at blobs and other trees. This is where filenames actually live.
commitA snapshot pointer: one root tree, zero or more parents, author, committer, message, optional signature.
tagAn annotated tag object: a named, described, optionally signed pointer at another object.

How the four fit together

Prove it to yourself with plumbing commands

Git splits its commands into porcelain (the friendly ones you use daily) and plumbing (the low-level ones scripts and the internals use). Plumbing is how you inspect the store directly.

# create a repository and one file
git init demo && cd demo
echo "hello" > a.txt

# hash the content the way Git would, without storing it
git hash-object a.txt
ce013625030ba8dba906f756967f9e9ca394464a

# that number is reproducible anywhere, with no Git at all:
printf 'blob %d\0' $(wc -c < a.txt) | cat - a.txt | sha1sum
ce013625030ba8dba906f756967f9e9ca394464a  -
# header is  "blob" SP <bytesize> NUL  then the raw content

# now actually store it and look at the store
git add a.txt
find .git/objects -type f
.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a
# first two hex chars = directory, remaining 38 = filename

git cat-file -t ce01362    # type
blob
git cat-file -p ce01362    # pretty-printed content
hello
git cat-file -s ce01362    # size in bytes
6

Anatomy of the .git directory

Everything Git knows lives here. Delete it and you have a plain folder of files. Copy it and you have copied the entire history.

objects/The store. objects/ab/cdef… are loose objects; objects/pack/*.pack and *.idx are packfiles.
refs/heads/Local branches. Each file contains one 40-character hash. A branch really is that small.
refs/tags/Tags, pointing either at a tag object or directly at a commit.
refs/remotes/Your last-known position of branches on each remote, updated by fetch.
HEADUsually the text ref: refs/heads/main. A raw hash here means detached HEAD.
indexThe staging area. A binary file listing paths, blob hashes, modes and stat data.
configRepository-local configuration, including remote URLs. reviewable A URL here can embed credentials.
hooks/Executable scripts run at lifecycle points. code execution Not transferred by clone, by design.
logs/The reflog. Every movement of every ref, with timestamps. Your undo buffer and your local audit trail.
packed-refsRefs compacted into one file for repositories with many branches or tags.
info/excludeIgnore rules that are local only and never committed.
COMMIT_EDITMSG, MERGE_HEAD, ORIG_HEADTransient state for in-progress operations. ORIG_HEAD is a lifeline after a bad reset or merge.
Threat — .git served over HTTP

If a web server exposes the .git directory of a deployed application, an attacker downloads .git/objects and reconstructs your entire source history, including the credentials you removed three commits later. This is one of the most reliably productive checks in a web assessment and it is still common in the wild.

Test: request /.git/HEAD. A response body of ref: refs/heads/main confirms exposure. Tools such as git-dumper automate the reconstruction from there.

Fix: deploy build artifacts rather than working trees; block dot-directories at the web server; keep .git outside the document root.

Loose objects, packfiles and delta compression

New objects are written individually and zlib-compressed. That is fine for hundreds of objects and terrible for millions, so Git periodically runs git gc, which rewrites many loose objects into a single packfile. Inside a pack, similar objects are stored as deltas against one another, which is where Git's remarkable storage efficiency comes from.

Two properties matter for security work. First, packing does not change object IDs: the hash still names the uncompressed content, so integrity is preserved across repacks. Second, garbage collection is what actually deletes unreachable objects, and it will not touch anything younger than gc.pruneExpire, which defaults to two weeks. That grace period is a safety net during recovery and an exposure window during incident response.

04 — Internals

Hashing, SHA-1 and the move to SHA-256

Git's entire integrity story rests on one assumption: you cannot find two different byte strings with the same hash. That assumption broke for SHA-1 in 2017, and the response is more interesting than the break.

Why the chain gives you tamper evidence

A commit's hash covers its tree hash, its parent hashes, the author and committer lines and the message. The tree's hash covers every filename, mode and blob hash beneath it. So a single changed byte in a file, three thousand commits ago, changes that blob's hash, which changes its tree, which changes that commit, which changes every descendant commit's hash. This is a Merkle tree, the same structure that underlies certificate transparency logs and blockchains.

The SHA-1 problem

SHA-1 has been theoretically weakened since 2005. Two practical milestones matter:

2017SHAttered — first public SHA-1 collision, two PDFs, same digest
2019SHA-1 chosen-prefix collision demonstrated, roughly $45k of compute
2020Chosen-prefix cost drops to about $45k and falling; GPG deprecates SHA-1
2.29Git version that introduced experimental SHA-256 repositories, in 2020

A collision alone is awkward for Git but not immediately catastrophic. A chosen-prefix collision is the dangerous kind: it lets an attacker craft two meaningfully different files, say a benign source file and a backdoored one, that hash identically. Push the benign one, get it reviewed and merged, then serve the malicious one to a client that fetches by hash and trusts what it gets.

Git's mitigation: hardened SHA-1

Since version 2.13, Git does not use plain SHA-1. It uses SHA-1DC (collision detection), the Stevens–Shumow algorithm that detects the specific message-block patterns produced by known collision attacks and refuses to proceed. A SHAttered-style PDF pair fed to modern Git produces an error, not a collision. This is a strong mitigation against known attack families and not a proof against future ones.

The real fix: SHA-256 repositories

git init --object-format=sha256 newrepo
# object IDs become 64 hex characters instead of 40
git hash-object -t blob --stdin <<< "hello"
5891b5b522d5df086d0ff0b110fbd9d21bb4fc7163af34d08286a2e846f6be03
Pitfall — SHA-256 interoperability

SHA-256 repositories still cannot interoperate with SHA-1 repositories. You cannot push a SHA-256 repository to a SHA-1 remote, and as of today GitHub does not host SHA-256 repositories. The planned bridge is an interop layer that keeps both hashes for every object; it is not finished. Treat SHA-256 as production-ready only for self-contained repositories on infrastructure you control.

What to actually do
  • Keep Git current so you get SHA-1DC and years of accumulated parser hardening.
  • Do not build a security control whose only assumption is "SHA-1 is collision-resistant".
  • Use signed tags and signed commits for anything you distribute. A signature covers the commit object, so it inherits whatever hash strength the repository has, but it adds an independent identity assertion.
  • For release artifacts, publish SHA-256 checksums alongside, and sign the checksum file.
05 — Internals

The three trees

Almost every confusing Git command becomes obvious once you know that Git manages three separate states of your project and each command moves data between specific pairs of them.

Reset: the command people fear

All three reset modes do the same first step, moving the current branch pointer. They differ only in how far the overwrite propagates.

CommandMoves branch refRewrites indexRewrites working treeUse it when
git reset --soft <c>yesnonoSquashing the last few commits into one. Changes stay staged.
git reset --mixed <c>yesyesnoThe default. Undo the commit and the staging, keep the edits.
git reset --hard <c>yesyesyesYou genuinely want the edits gone. Uncommitted work is unrecoverable.
Pitfall — the one thing Git cannot recover

Committed work is almost always recoverable through the reflog, even after a hard reset. Uncommitted work is not. git reset --hard, git checkout . and git clean -fd destroy changes that were never turned into objects, and no Git command will bring them back. When in doubt, git stash first. A stash is a real commit.

Staging with intent

git add -p              # interactive hunk-by-hunk staging — read your own diff
git add -N <file>       # record a new file's existence so it shows up in git diff
git restore --staged .   # unstage everything, keep the edits
git status --short       # XY format: X = index state, Y = working tree state
git diff --staged        # review exactly what you are about to commit
Habit that prevents most secret leaks

Use git add -p and git diff --staged rather than git add .. The overwhelming majority of credential leaks in public repositories are accidental: a .env, a terraform.tfstate, a kubeconfig, a service-account JSON, or an IDE settings file swept up by a bulk add. Reading your own staged diff before every commit costs seconds and catches nearly all of them.

06 — Internals

Refs, HEAD and the reflog

A branch is a forty-byte text file. Understanding that removes most of the anxiety about branching and explains exactly how work gets lost and how it gets recovered.

cat .git/refs/heads/main
7e3d19f8c2a1b4e0d6f39a5c7b2e18d0a4c96f31

cat .git/HEAD
ref: refs/heads/main            # a symbolic ref — HEAD points at a branch

# the reference hierarchy
refs/heads/<name>               # local branches
refs/tags/<name>                # tags
refs/remotes/<remote>/<name>    # remote-tracking branches, updated by fetch
refs/notes/, refs/stash, refs/pull/<n>/head   # notes, stash, GitHub PR refs

Attached versus detached HEAD

The reflog: your local audit trail

Every time a ref changes value, Git appends a line to .git/logs/. This is entirely local, is never pushed or fetched, and is the reason destructive-looking Git operations are usually reversible.

git reflog
7e3d19f HEAD@{0}: commit: add rate limiting
b204ae8 HEAD@{1}: reset: moving to HEAD~1
91fc37d HEAD@{2}: rebase (finish): returning to refs/heads/main
4ac82e5 HEAD@{3}: checkout: moving from main to feature/otp
d15c6ae HEAD@{4}: pull --rebase: checkout d15c6ae

git reflog show main        # history of one branch pointer specifically
git reflog --date=iso       # absolute timestamps, which is what you want for forensics

# recover a branch you deleted or a commit you reset away
git switch -c recovered 91fc37d
# or point the branch back where it was
git reset --hard main@{2}
Forensic value

The reflog answers questions the commit graph cannot: when did this developer's clone first see this commit, was there a force-push, did someone reset a branch backwards. Entries carry wall-clock timestamps and the operation that caused them. During an investigation on a developer workstation, capture .git/logs/ before anything else, because gc.reflogExpire defaults to 90 days for reachable entries and 30 days for unreachable ones, and any Git command may trigger expiry.

Pitfall — the reflog does not exist on the server

Bare repositories on servers typically have reflogs disabled (core.logAllRefUpdates defaults to false for bare repos). GitHub keeps its own internal audit trail instead, exposed through the org audit log and the Events API, not through Git. Do not plan an investigation around reflog data you have not confirmed exists.

Revision syntax you will actually use

HEAD~3Three commits back, always following the first parent. The linear ancestor.
HEAD^2The second parent of a merge commit. ^ chooses which parent, ~ chooses how far back.
main@{2}Where main pointed two reflog entries ago.
main@{yesterday}Where main pointed at that time, by reflog. Also @{2.weeks.ago}.
A..BCommits reachable from B but not A. The default "what is new" range.
A...BSymmetric difference: reachable from either but not both. What git log --left-right shows.
:/fix loginThe most recent commit whose message matches that text.
HEAD:path/to/fileThe blob at that path in that commit. Feed it to git show.
07 — History

Branching and merging

Branching in Git is cheap because a branch is a pointer. Merging is where the real algorithm lives, and where review controls either hold or fail.

git switch -c feature/otp      # create and switch (modern form)
git checkout -b feature/otp    # same thing, older form still everywhere
git branch -vv                 # local branches, upstreams, ahead/behind counts
git branch -d feature/otp      # delete only if merged
git branch -D feature/otp      # delete regardless — the commits survive in the reflog
git switch -                    # back to the previous branch

Two kinds of merge

Resolving conflicts

# conflict markers Git writes into the file
<<<<<<< HEAD
timeout = 30            # ours — the branch you are merging INTO
=======
timeout = 60            # theirs — the branch being merged IN
>>>>>>> feature/otp

# see all three versions, not just two — this is what people forget
git config merge.conflictStyle zdiff3   # now the base version is shown too

git status                       # "both modified" lists the conflicts
git diff                         # combined diff of conflicted files
git checkout --ours  <file>     # take our side wholesale
git checkout --theirs <file>    # take their side wholesale
git add <file>                   # staging a file marks it resolved
git merge --continue
git merge --abort                # back to the pre-merge state, always safe

git config rerere.enabled true   # remember conflict resolutions and replay them
Threat — the conflict resolution blind spot

On GitHub, the diff shown for a pull request is normally the change against the merge base. A merge commit's own content is not reviewed the same way: if a developer resolves a conflict by hand, the resolution can introduce code that appears in neither parent and that no reviewer ever looked at. This is a genuine and repeatedly exploited way to smuggle a change past review.

Detection: git log --cc --merges shows a combined diff that reveals content unique to the merge commit. Also inspect git diff HEAD^1 HEAD ; git diff HEAD^2 HEAD. Requiring linear history, or a merge queue that re-runs checks on the final result, removes the class entirely.

Merge strategies worth knowing

--no-ffAlways create a merge commit, preserving the fact a branch existed. Common policy for auditability.
--squashCombine all branch work into one commit on the target, with no merge link. Clean history, lost granularity, and the branch shows as unmerged.
-X ours / -X theirsAuto-resolve conflicting hunks by preferring one side. Not the same as the ours strategy.
-s oursRecord a merge but discard the other side's changes entirely. Used to mark a branch as merged without taking its content. Dangerous if misunderstood.
--verify-signaturesRefuse to merge if the commits being merged are not validly signed. Underused.
08 — History

Rebase and rewriting history

Rebase does not move commits. It cannot: commits are immutable. Rebase replays the changes as brand new commits with new hashes, then abandons the originals.

Interactive rebase

git rebase -i HEAD~5          # edit the last five commits
git rebase -i --root          # rewrite from the very first commit

# the todo list you get, one line per commit:
pick   4ac82e5 add otp endpoint
reword 91b0f7d fix typo in ottp        # change the message only
squash 7e3d19f address review comments  # fold into the previous commit
fixup  b204ae8 lint                     # squash but discard this message
edit   d15c6ae add secret key           # stop here so you can amend the content
drop   0e5b8d2 debug printf             # remove the commit entirely

git rebase --continue | --skip | --abort
git commit --amend            # rewrite only the most recent commit
git rebase --onto main old-base feature   # transplant a range onto a new base
The golden rule, and its real reason

Do not rebase commits that others have based work on. Because rebase produces new objects, everyone who already fetched the old ones now has a divergent history. Their next pull tries to merge the old and new lines, producing duplicated commits and conflicts that look inexplicable.

When you must force-push, use --force-with-lease rather than --force. Lease checks that the remote ref is still where you last saw it, so you cannot silently destroy a colleague's commit that landed in the meantime. Better still, --force-with-lease --force-if-includes, which also verifies your local ref actually incorporates what you fetched.

Threat — history rewriting as an anti-forensic technique

An attacker with push access to an unprotected branch can rewrite history to remove evidence: drop the commit that added a backdoor, amend a commit so a malicious change appears under a colleague's name, or forge author dates so activity falls outside a review window. Because rebase strips signatures by default, a rewritten history also quietly loses whatever cryptographic attribution existed.

Controls: deny force-push on protected branches for everyone including admins; enable GitHub's block force pushes ruleset; require signed commits so rewritten commits fail verification; and treat force-push events in the audit log as alertable, because on a protected branch they should be impossible.

Cherry-pick, revert and the safe alternative

git cherry-pick <commit>          # replay one commit here, as a new object
git cherry-pick -x <commit>       # append "(cherry picked from …)" — do this for traceability
git cherry-pick A..B              # a range

git revert <commit>               # create a NEW commit that undoes it — safe on shared branches
git revert -m 1 <merge-commit>    # revert a merge, keeping mainline parent 1

revert is the only undo that is safe on published history, because it adds rather than rewrites. For anything already pushed to a branch other people use, reach for revert first and treat rewriting as an incident-response action requiring coordination.

09 — Distributed Git

Remotes and the wire protocols

A remote is a named URL plus a set of refspecs. Everything about pushing and pulling follows from that, including several security properties people assume Git provides and it does not.

Remotes and refspecs

git remote -v
origin  git@github.com:acme/api.git (fetch)
origin  git@github.com:acme/api.git (push)

git remote add upstream https://github.com/original/api.git
git remote set-url origin git@github.com:acme/api.git
git remote show origin          # branches, tracking, and what push would do
git remote prune origin         # drop remote-tracking refs for deleted branches

# a refspec is  +<src>:<dst>   — the + means "allow non-fast-forward"
fetch = +refs/heads/*:refs/remotes/origin/*

# GitHub exposes pull requests as refs you can fetch directly:
git fetch origin +refs/pull/*/head:refs/remotes/origin/pr/*
git switch --detach origin/pr/42   # review PR 42 locally

What actually happens on the wire

Both the SSH and HTTPS transports run the same smart protocol. The exchange has three phases:

  1. Reference discovery. The server advertises every ref and its object ID, plus the capabilities it supports. Over HTTPS this is GET /info/refs?service=git-upload-pack.
  2. Negotiation. The client sends want lines for objects it needs and have lines for objects it already holds. The two sides converge on a minimal set. Protocol v2, now the default, lets the client filter refs server-side instead of receiving the entire advertisement, which matters enormously on repositories with tens of thousands of refs.
  3. Packfile transfer. The server streams a packfile containing only the missing objects. The client verifies and indexes it.
GIT_TRACE_PACKET=1 git fetch origin     # watch the protocol conversation
GIT_TRACE=1 GIT_CURL_VERBOSE=1 git fetch # full HTTP debugging
git config --global protocol.version 2   # default since Git 2.26, verify it is on

# restrict which transports Git will ever use
git config --global protocol.allow never
git config --global protocol.https.allow always
git config --global protocol.ssh.allow always
Threat — transport and credential exposure
  • The git:// protocol has no authentication, no encryption and no server verification. Anyone on the path can serve you arbitrary code. GitHub disabled it entirely in 2022. If you find it in a Dockerfile, a submodule URL or a package manifest, treat it as a finding.
  • Credentials in remote URLs. https://user:token@github.com/… writes the token into .git/config in plaintext, into every git remote -v output, and often into CI logs. Use a credential helper or SSH instead.
  • ~/.git-credentials is plaintext by design. The store helper is a file of https://user:password@host lines with no encryption. Prefer osxkeychain, wincred/manager, libsecret, or cache with a short timeout.
  • SSH host key verification is your only defence against a machine-in-the-middle. Typing "yes" to an unknown fingerprint on a hostile network defeats it. Pre-seed known_hosts from GitHub's published fingerprints, and set StrictHostKeyChecking yes in CI images.
  • http.sslVerify=false disables TLS validation. It appears in countless internal CI configs to work around a corporate proxy. It converts HTTPS into git:// with extra steps.
Safe defaults to set once, globally 
git config --global pull.ff only             # never a surprise merge commit
git config --global push.default simple      # push only the current branch, to its upstream
git config --global transfer.fsckObjects true
git config --global fetch.fsckObjects true
git config --global receive.fsckObjects true # reject malformed/malicious objects
git config --global core.fsmonitor false     # unless you need it and trust the repo
git config --global init.defaultBranch main
git config --global credential.helper manager # or osxkeychain / libsecret

fsckObjects is the underrated one. It makes Git validate the structure of every object it receives, which has blocked several real object-parsing exploits. It costs a little transfer speed and is worth it.

10 — Daily practice

The daily command set

Organised by the question you are actually asking, rather than alphabetically.

Starting

git init                          # create .git in the current directory
git init --bare shared.git        # a server-side repo: no working tree
git clone <url> [dir]
git clone --depth 1 <url>         # shallow: latest commit only, fast, no history
git clone --filter=blob:none <url> # blobless partial clone: full graph, blobs on demand
git clone --single-branch --branch release <url>

Recording

git status -sb                    # short format with branch line
git add -p                        # stage interactively — read every hunk
git commit -m "msg"
git commit -v                     # show the staged diff in the editor while writing the message
git commit --amend --no-edit      # fold staged changes into the last commit
git commit --fixup <sha>          # marked for autosquash later
git rebase -i --autosquash <base> # apply all the fixups

Inspecting

git log --oneline --graph --decorate --all   # the one alias everyone ends up making
git log -p -- path/to/file        # full patch history for one path
git log --follow -- file          # keep tracking across renames
git log -S "AWS_SECRET"           # pickaxe: commits that changed the COUNT of this string
git log -G "regex"                # commits whose diff text matches this regex
git log --author="jane" --since="2 weeks"
git log --diff-filter=D -- path   # when was this file deleted, and by whom
git show <commit>:path/to/file    # the file's contents at that commit
git blame -w -C -C <file>         # ignore whitespace, detect moved/copied code
git shortlog -sn                  # commit counts per author
git bisect start / bad / good     # binary search for the commit that introduced a bug
git bisect run ./test.sh          # fully automated bisect
The pickaxe is a security tool

git log -S is the fastest way to answer "when did this string enter the repository and when did it leave". Run it against a leaked credential fragment, a suspicious domain, a base64 blob, or the name of a function you do not recognise. Add --all to search every ref, and --pickaxe-regex for patterns. git log -G is the regex sibling and catches changes that keep the occurrence count the same.

Undoing

git restore <file>                # discard working-tree changes
git restore --staged <file>       # unstage
git restore --source=HEAD~3 <file>
git revert <commit>               # safe undo on shared history
git reset --soft|--mixed|--hard <c>
git clean -nd                     # DRY RUN first, always
git clean -fd                     # delete untracked files and dirs
git stash push -m "wip" -u         # -u includes untracked files
git stash list / show -p / pop / drop

Sharing

git fetch --all --prune --tags
git pull --rebase                 # linear alternative to a merge-pull
git push -u origin feature/otp    # push and set upstream
git push --force-with-lease       # the only acceptable force
git push origin --delete old-branch
git push --tags                   # tags are NOT pushed by default
Pitfall — three defaults that surprise people
  • Tags do not push automatically. A release tag that exists only locally will confuse everyone, including your release pipeline.
  • Empty directories cannot be tracked. Git tracks files, not directories. Teams add a .gitkeep by convention.
  • File modes are barely tracked. Git records only whether a file is executable (100644 versus 100755). It does not record ownership or full permissions, so do not use Git as a deployment mechanism that needs to preserve them.

Ignore rules, attributes and hooks

.gitignore and its layers

Ignore rules are consulted in a defined order, and the first match wins within a file, with later patterns overriding earlier ones.

.gitignoreCommitted, shared with the team. Belongs to the project.
.git/info/excludeLocal to your clone, never committed. Your personal noise.
core.excludesFileGlobal, across all repositories. Set it to ~/.gitignore_global for editor and OS junk.

# pattern syntax
*.log                 # any .log anywhere

git check-ignore -v path/to/file   # WHICH rule is ignoring this? invaluable

git rm --cached <file>             # stop tracking without deleting from disk
Threat — .gitignore is not a security control

Two failure modes cause real incidents. First, ignore rules do not apply to already-tracked files. Adding .env to .gitignore after committing it changes nothing; the file keeps being tracked and every future change is committed. You need git rm --cached .env as well, and the old content still sits in history forever.

Second, an ignored file is invisible to review but present on disk. Attackers rely on this: a malicious build script referenced by an ignored path, or a .gitignore entry added in the same pull request that adds the file it hides. Treat changes to .gitignore in a security-relevant pull request as something to read, not skim.

Pitfall — attributes can hide changes from reviewers

This is convenient for lockfiles and lethal for review: a pull request can modify a suppressed file and the change will be hidden behind a "load diff" the reviewer never clicks. If you suppress a file, make sure something else, such as a dependency-review check or a CODEOWNERS entry, still forces a human to look at it.

Threat — hooks as a code execution primitive

Client-side hooks are the reason git clone of an untrusted repository has repeatedly been a code execution vector. Hooks are deliberately not cloned, so attackers look for ways to write into .git/ anyway. CVE-2024-32002 is the clearest example: a repository with submodules could, on case-insensitive filesystems, be crafted so that a checkout wrote files into .git/hooks/, giving remote code execution on git clone --recursive. CVE-2021-21300 abused clean/smudge filters for the same end.

Defences: keep Git patched, this class recurs; do not run --recursive clones of untrusted repositories; clone suspicious repositories inside a container or VM; set core.symlinks=false and core.protectNTFS=true / core.protectHFS=true where relevant; and remember that core.fsmonitor and diff.external in a repository-local config are also execution vectors, which is why Git introduced safe.directory and refuses to read config from repositories owned by other users.

12 — Daily practice

Submodules, subtrees, LFS and worktrees

Submodules

A submodule pins another repository at an exact commit. The parent stores a .gitmodules file with the URL and a special gitlink tree entry holding the child's commit hash.

git submodule add https://github.com/acme/lib vendor/lib
git clone --recurse-submodules <url>
git submodule update --init --recursive
git submodule update --remote       # move the pin to the child's latest — a real change, review it
git submodule status
git -c protocol.file.allow=never submodule update   # block file:// submodule URLs
Threat — submodules are a supply chain edge
  • The URL is attacker-influenced data. A pull request that edits .gitmodules to point at a different host redirects your build's dependency. In a diff this is one changed line that is easy to wave through.
  • Pin drift. --remote silently advances the pin to whatever the upstream now has. If the upstream is compromised, you inherit it on the next update.
  • Parser history. CVE-2018-11235 allowed arbitrary code execution through a crafted .gitmodules; CVE-2019-1387 and CVE-2024-32002 continued the theme. Recursive clone of untrusted content is genuinely dangerous.
  • Deleted upstream. If the referenced repository or commit disappears, your build breaks or, worse, someone re-registers the namespace and serves different content.

Controls: require review on .gitmodules via CODEOWNERS; mirror third-party dependencies into your own organisation rather than referencing them directly; pin to full commit hashes and change them deliberately; disable protocol.file.

Subtrees, the alternative

git subtree add --prefix=vendor/lib https://github.com/acme/lib main --squash
git subtree pull --prefix=vendor/lib https://github.com/acme/lib main --squash

A subtree copies the dependency's files into your repository. Clones are simple, no extra commands are needed, and the code is visible to your scanners and reviewers. The cost is a bigger repository and a more awkward path for contributing changes upstream. For security-sensitive dependencies the visibility is often worth it.

Git LFS

git lfs install
git lfs track "*.psd" "*.bin"       # writes rules into .gitattributes
git lfs ls-files

LFS replaces large files in the repository with small pointer files and stores the real content on a separate server. Two consequences matter: LFS content lives outside the Git object model, so it is not covered by commit hashes in the way ordinary blobs are, and your secret scanning may not see it unless it is LFS-aware. Confirm that before assuming coverage.

Worktrees

git worktree add ../hotfix release/2.4   # a second working tree, same object store
git worktree list
git worktree remove ../hotfix

Worktrees let you have several branches checked out simultaneously without cloning again. They are the correct answer to "I need to fix production but I am mid-refactor", and far safer than stashing under pressure.

13 — GitHub

Forks, pull requests and the collaboration model

The pull request is where Git's total absence of access control meets a real authorization system. Almost every platform-level control you configure is ultimately about what can reach the default branch.

The mechanics

ForkA server-side copy in your namespace. On GitHub, forks of a public repository share an object store with the upstream network, which has an important security consequence covered in section 18.
Pull requestA request to merge a head ref into a base ref, plus review state, checks, and discussion. GitHub exposes it as refs/pull/<n>/head and a computed refs/pull/<n>/merge.
Draft PRCannot be merged and does not request review. Useful for early feedback.
Merge commitStandard merge, preserves all commits and adds a merge node.
Squash and mergeOne commit on the base, authored by the contributor, committed by GitHub. Clean, but discards individual commit signatures.
Rebase and mergeReplays each commit onto the base. New hashes, signatures stripped, linear history.
Merge queueSerialises merges and re-runs checks against the actual resulting tree. The correct fix for "it passed in the PR and broke on main".
Pitfall — squash and rebase merges destroy signatures

If your policy is "all commits on main must be signed by their author", note that squash and rebase merges create new commit objects. GitHub signs them with its own key, so the branch shows Verified but the attestation is now "GitHub performed this merge", not "the author wrote this code". If author attribution matters to you, require merge commits, or accept that your real assurance comes from the review record rather than the signature.

Reviewing a pull request properly

  • Read the diff against the merge base, then check the merge result. Use the Files changed view but also fetch the branch and run git diff main...pr-branch yourself for anything sensitive.
  • Look at what is not code. Workflow files, .gitignore, .gitattributes, .gitmodules, lockfiles, Dockerfiles, and anything under .github/ deserve more attention than application code, because they change what runs rather than what the application does.
  • Check the commit list, not just the aggregate diff. A commit can add and later remove a secret; the aggregate diff shows nothing while the object remains in history forever.
  • Watch for force-pushes after approval. GitHub can be configured to dismiss stale approvals on new commits. If it is not, an approved PR can be rewritten before merge.
  • Be suspicious of large, mechanical diffs. Reformatting, generated files and vendored dependencies are where hostile changes hide.
Threat — Trojan Source and invisible characters

Unicode bidirectional control characters can make source code render differently from how a compiler parses it. A reviewer sees a comment; the compiler sees executable code. Homoglyph attacks substitute visually identical characters so that сheck_auth (Cyrillic с) is a different identifier from check_auth. Zero-width characters hide payload boundaries.

Defences: GitHub now warns on bidirectional Unicode in diffs, but do not rely on the UI alone. Add a CI check that rejects U+202A–U+202E, U+2066–U+2069, U+200B–U+200D and non-ASCII identifiers outside expected files. git diff --ita-visible-in-index will not help here; grep -P "[\x{202A}-\x{202E}\x{2066}-\x{2069}]" across the diff will.

The second major class. GitHub interpolates ${{ }} expressions into the shell script before the shell runs, so a value containing shell metacharacters becomes shell code. Pull request titles, branch names, issue bodies and commit messages are all attacker-controlled.

Threat — the mutable tag problem, demonstrated in the wild

uses: some/action@v3 resolves a mutable Git tag. Whoever controls that repository can repoint the tag at any commit, and your next run executes different code with your secrets. In March 2025 the tj-actions/changed-files action was compromised exactly this way: existing version tags were repointed to a malicious commit that dumped runner memory, and thousands of repositories printed their own secrets into public build logs.

Controls: pin every third-party action to a full 40-character commit SHA with the version in a trailing comment; enable Dependabot to bump the SHAs so pinning stays maintainable; restrict which actions can run at all through organisation policy (allow only actions created by GitHub plus a verified allowlist); and for critical pipelines, fork the action into your own organisation and reference your fork.

Threat — self-hosted runners

GitHub-hosted runners are destroyed after every job. Self-hosted runners, by default, are not. That single difference creates a chain of problems: a malicious job can persist a backdoor for the next job, harvest credentials left by other pipelines, read the Docker socket, and pivot into the network the runner sits in. On a public repository, attaching a self-hosted runner to a workflow reachable from fork pull requests is effectively offering remote code execution inside your network.

Controls: never use self-hosted runners on public repositories; use ephemeral runners (--ephemeral) or the Actions Runner Controller so each job gets a fresh container; place runners in an isolated network segment with egress filtering; scope them to specific repositories rather than the whole organisation; and never grant them a cloud instance profile with broad permissions.

Other Actions risks worth naming

Cache poisoningCaches are scoped by branch, and a PR branch can write a cache that the base branch later restores. Do not cache anything that gets executed without verification.
Artifact poisoningA workflow_run workflow that downloads and executes an artifact produced by an untrusted PR run is executing attacker code with the base repository's privileges.
Log exfiltrationSecret masking is string matching. Base64-encode, reverse, or split a secret and it prints in cleartext. Treat build logs of any workflow with secrets as sensitive.
Composite and reusable workflowsThey inherit the caller's permissions and can receive secrets: inherit. Review them as carefully as the caller.
Dangerous defaultOlder organisations still have workflow permissions set to read and write by default. Change it to read-only at the organisation level, then grant per-workflow.
Fork approvalRequire approval for all outside contributors before their workflows run. It is a per-repository setting, and the default is weaker than you want.

The migration that matters most

Classic personal access tokens with the repo scope and no expiry are the most common high-severity finding in a GitHub configuration review. Pitfall — the OIDC subject wildcard

Binding to repo:org/name:* means any branch or pull request in that repository can assume the production role.   • Require MFA organisation-wide. Prefer passkeys or a hardware security key. TOTP is acceptable; SMS is not.

  • Authorise PATs and SSH keys for SSO explicitly. This is the control that stops a pre-existing personal token from continuing to work after SSO is enabled.
  • Review third-party OAuth apps and installed GitHub Apps quarterly. An OAuth app the user approved in 2019 may still hold repo scope across the organisation.
  • Restrict organisation membership visibility and repository creation so that a compromised low-privilege account cannot create a public repository containing internal code.

17 — Trust

Commit signing and provenance

Git records who claims to have written a commit. It does not check. This section is about closing that gap, and about the several ways the fix is misunderstood.

The problem, demonstrated

# two lines of config and every commit I make is attributed to someone else
git config user.name  "Linus Torvalds"
git config user.email "torvalds@linux-foundation.org"
git commit -m "totally legitimate change"

git log -1 --format='%an <%ae>'
Linus Torvalds <torvalds@linux-foundation.org>

# push it to any repository you can write to, and GitHub will even link the
# commit to that person's profile if the email matches their account

There is no vulnerability here. Git was designed for a mailing-list workflow where trust came from the maintainer reading the patch, not from the metadata. But it means the author field is unverified user input, and any control that reads it, an audit report, a compliance metric, an alerting rule, is reading attacker-controlled data unless signatures are enforced.

Setting up signing

SSH signing is the pragmatic choice now: developers already have SSH keys, there is no keyring to manage, and hardware-backed keys work out of the box.

# --- SSH signing (simplest, recommended) ---
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
git config --global tag.gpgSign true

# to verify locally you also need an allowed-signers file
echo "jane@corp.example $(cat ~/.ssh/id_ed25519.pub)" >> ~/.git-allowed-signers
git config --global gpg.ssh.allowedSignersFile ~/.git-allowed-signers
# then add the SAME key to GitHub as a SIGNING key — the authentication key
# entry does not grant signature verification

# --- GPG signing ---
gpg --full-generate-key                 # ed25519 or 4096-bit RSA
gpg --list-secret-keys --keyid-format=long
git config --global user.signingkey <KEYID>
git config --global commit.gpgsign true
gpg --armor --export <KEYID>              # paste into GitHub → SSH and GPG keys

# --- verifying ---
git log --show-signature -3
git verify-commit HEAD
git verify-tag v2.1.0
git merge --verify-signatures feature/otp
git config --global merge.verifySignatures true

# --- hardware-backed, the strongest practical option ---
ssh-keygen -t ed25519-sk -C "jane@corp yubikey"   # private key never leaves the token
Vigilant mode

Enable Flag unsigned commits as unverified in your GitHub account settings. Without it, an unsigned commit simply shows no badge, which readers interpret as normal. With it, unsigned commits attributed to you are explicitly marked Unverified, so an impersonation attempt is visible rather than merely unremarkable. Enable it once you sign consistently.

Signed tags and release provenance

git tag -s v2.1.0 -m "release 2.1.0"     # annotated AND signed
git tag -v v2.1.0
git push origin v2.1.0

18 — Offense

Secrets in history

This is the most common serious Git security incident by a very wide margin, and the standard remediation instinct is the wrong one.

The core mechanic is simple and counterintuitive to newcomers: deleting a file in a new commit does not remove it from history. The blob object still exists, still has a hash, and is still reachable through every commit that contained it. Anyone with the repository can retrieve it in one command.

# a secret committed in March and "removed" in April
git log --all --diff-filter=D --name-only -- .env
git log -S "AKIA" --all --oneline          # when did this string appear and vanish
git show <old-commit>:.env                 # and here it is, in full

# enumerate every blob ever, largest first — finds what nobody remembers committing
git rev-list --objects --all |
  git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' |
  awk '$1=="blob"' | sort -k3 -nr | head -40

Detection

#  · ask GitHub Support to garbage-collect the fork network and purge cached views

#  · invalidate CI caches that may hold the old objects
#  · re-run the scan to confirm
git count-objects -v              # confirm the objects are gone locally
Pitfall — rewriting breaks everything downstream

A history rewrite changes every commit hash from the rewrite point forward. Open pull requests break, signed commits lose verification, references in issues and tickets point at commits that no longer exist, deployment records that name a commit hash become dangling, and any clone that pulls instead of re-cloning will reintroduce the old history. Plan a rewrite as a coordinated change with a communication step, not as a quick fix.

Prevention that works
  • Push protection on, organisation-wide, with bypass requiring a written reason.
  • Pre-commit hooks distributed via core.hooksPath, so they are shared and versioned.
  • A real secret manager: Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault. Applications read at runtime; nothing is ever in the repository.
  • OIDC for cloud access, so the highest-value credentials do not exist as strings.
  • .env.example with placeholder values committed, and .env ignored from day one.
  • Short-lived everything. A credential with a one-hour lifetime is a far smaller incident than one with no expiry.
  • Scan the whole history when onboarding a repository, not just new commits. The problem is usually already there.
19 — Offense

Supply chain attacks on Git and GitHub

Attacking the pipeline that builds software is more efficient than attacking the software. These are the paths, roughly in order of how often they are actually used.

The named techniques

Repojacking

When a GitHub user or organisation is renamed or deleted, the old owner/repo path can become claimable by someone else. Anything still referencing that path, a Go module, a submodule, an install script, a Dockerfile, a GitHub Action, silently starts pulling attacker content. GitHub retires popular names, but the long tail of internal references is where this lands. Control: pin dependencies to commit hashes, vendor or mirror critical dependencies, and audit for references to repositories that now redirect.

Dependency confusion

A build configured with both a private and a public registry may resolve an internal package name to a public package of the same name with a higher version. Control: use scoped or namespaced package names, configure the package manager to route those scopes exclusively to the private registry, and never let a public registry be a fallback for internal names.

Maintainer compromise and slow social engineering

The xz-utils backdoor of 2024 is the reference case. An attacker spent roughly two years building a contribution history, applied pressure through sockpuppet accounts to have the original maintainer hand over release authority, and then shipped a backdoor in the release tarball rather than in the Git repository, so the malicious content was never visible in the commit history anybody reviewed.

The lesson people take from xz, and the one they should

The common takeaway is "review your dependencies more carefully". The more useful takeaway is that the release artifact and the source repository were different, and nothing in the process checked that they matched. Reproducible builds and build-from-source provenance detect this class. Code review does not, because the malicious code was never in the code.

Malicious commits through the review process

Hostile changes are made to look boring: a plausible bug fix that introduces an off-by-one in a bounds check, an added dependency in a lockfile-only commit, a change to a test that makes it stop asserting anything, a refactor that quietly removes a check. The 2021 University of Minnesota "hypocrite commits" episode demonstrated the whole class against the Linux kernel and got the university banned from contributing.

Dangling and hidden commits

A commit pushed and then removed from all branches remains fetchable by hash. Attackers use this to stage payloads that are invisible in the UI but retrievable by a build that fetches a specific SHA. Detection: git fsck --unreachable --dangling locally, and on GitHub, watch the Events API for pushes whose commits are not on any branch.

xz2024 — release tarball differed from the reviewed repository
tj-actions2025 — version tags repointed, secrets dumped to public logs
Codecov2021 — modified bash uploader exfiltrated CI environment variables
SolarWinds2020 — build system compromised, source repository clean

Three of those four attacked the build, not the source. That is the strategic point of this whole section: your code review process can be perfect and still ship a backdoor, if what you ship is not provably the thing you reviewed.

Hardening checklists

Four layers, in the order you should work through them. Everything here appears somewhere above with its reasoning; this is the condensed operational form.

Developer workstation

  • Keep Git current Object-parsing and clone-time code execution bugs recur. This is not optional maintenance.
  • Full-disk encryption and screen lock A cloned repository is your entire source history sitting on a laptop.
  • Hardware-backed SSH keys ssh-keygen -t ed25519-sk, with a passphrase. The private key cannot be exfiltrated by malware.
  • No plaintext credential storage Use osxkeychain, manager, or libsecret. Never the store helper, never credentials in a remote URL.
  • Signing on by default commit.gpgsign true and tag.gpgSign true, globally.
  • Safe transport config protocol.allow never with explicit allows for https and ssh; never http.sslVerify false.
  • Object validation on transfer.fsckObjects, fetch.fsckObjects, receive.fsckObjects all true.
  • Pre-commit secret scanning Shared through core.hooksPath so the whole team gets it.
  • Global gitignore for .env, *.pem, *.key, id_rsa, .aws/, *.kubeconfig, IDE and OS files.
  • Untrusted repositories go in a container Especially with --recurse-submodules.
  • Review IDE and editor extensions They run with your privileges and can read every repository you have.

Repository

  • Ruleset on the default branch PR required, approvals required, stale approvals dismissed, force-push and deletion blocked, administrators included.
  • Required status checks Build, tests, SAST, dependency review, secret scan. In strict mode so branches must be current.
  • CODEOWNERS covering the dangerous paths .github/workflows/, CODEOWNERS itself, .gitmodules, Dockerfiles, infrastructure code, lockfiles.
  • Secret scanning with push protection Enabled, with bypasses requiring justification.
  • Dependabot alerts and security updates On, with someone actually triaging them.
  • Signed commits required Once the team is set up for it.
  • Default workflow permissions read-only Grant write per workflow, per job.
  • Forking of private repositories disabled
  • SECURITY.md and private vulnerability reporting So reports reach you instead of Twitter.
  • Deploy keys audited Read-only unless there is a written reason. Write keys bypass branch protection.
  • Archive, do not delete Preserves history and audit trail.

Organisation

  • MFA required for all members Passkeys or hardware keys preferred.
  • SAML SSO with SCIM So that leaving the company actually removes access.
  • Classic PAT creation disabled Fine-grained tokens with approval, or GitHub Apps.
  • Third-party application access restricted An approval list, reviewed quarterly.
  • Base permissions set to none or read Grant through teams, not organisation defaults.
  • Actions policy: allow only GitHub-authored and explicitly listed actions
  • Self-hosted runners never attached to public repositories Ephemeral, network-isolated, repository-scoped.
  • Organisation-level rulesets So a new repository is protected on day one, not when someone remembers.
  • Audit log streaming to your SIEM The audit log is your only durable server-side evidence.
  • Quarterly access review Members, outside collaborators, teams, apps, deploy keys, tokens.
  • Offboarding runbook That includes revoking tokens, SSH keys, and app authorisations, not just disabling the account.

CI/CD

  • Every third-party action pinned to a full commit SHA With the version in a trailing comment and Dependabot maintaining it.
  • No pull_request_target combined with a checkout of the PR head If you cannot remove it, split into a build stage and a privileged comment stage.
  • All untrusted context values routed through env: Never interpolated into a run: block.
  • Least-privilege permissions: at the top of every workflow Start at contents: read.
  • OIDC instead of stored cloud credentials With the subject claim bound to a branch or environment, never a wildcard.
  • persist-credentials: false on checkout Unless the job genuinely needs to push.
  • Dependency install without lifecycle scripts npm ci --ignore-scripts and equivalents.
  • timeout-minutes on every job Bounds a compromised or hung runner.
  • Environments with required reviewers for production A human approval between merge and deploy.
  • Build provenance attestations generated and verified at deploy Deploy by digest, never by mutable tag.
  • Approval required for outside-contributor workflow runs
  • Treat build logs as sensitive Masking is best-effort string matching, not a control.

Two related jobs: reconstructing what happened during an incident, and producing evidence that a change control operated as designed.

Investigating a repository

Signals worth alerting on
  • Force push to a protected branch. Should be impossible. If it happens, either the protection is misconfigured or someone used a bypass.
  • A commit whose author and committer emails differ in a repository where rebasing is not the norm.
  • Author timestamp in the future or before the repository existed.
  • Changes to .github/workflows/, CODEOWNERS, or ruleset configuration, especially outside working hours or from an unusual location.
  • A new deploy key, especially one with write access.
  • A PAT or SSH key created and then used from a different geography within minutes.
  • A repository changing from private to public.
  • An organisation member's role escalated to owner.

Recovery playbook

Ordered by how often you will need them. The first rule of Git recovery: if it was ever committed, it almost certainly still exists.

Committed to the wrong branchgit switch right-branch, then git cherry-pick <sha>, then go back and git reset --hard HEAD~1 on the wrong one.
Need to undo the last commit, keep the workgit reset --soft HEAD~1. The changes return to the index.
Bad commit already pushed to a shared branchgit revert <sha>. Never rewrite shared history for a routine mistake.
Deleted a branchgit reflog to find the tip, then git switch -c <name> <sha>.
Hard reset destroyed committed workgit reflog, find the pre-reset entry, git reset --hard HEAD@{n}.
Rebase went wrong mid-flightgit rebase --abort. If already finished, git reset --hard ORIG_HEAD.
Commits made on a detached HEADgit reflog, then git branch rescue <sha>. Do it before garbage collection runs.
Dropped a stashgit fsck --unreachable | grep commit, inspect candidates with git show, then git stash apply <sha>.
Force-pushed over a colleague's workAsk them for their local git reflog and push the recovered tip. This is why --force-with-lease exists.
Merge conflict panicgit merge --abort or git rebase --abort. Both return you exactly to the pre-operation state.
Committed a secret, not yet pushedAmend or reset it away, then still rotate if it ever touched a shared machine.
Committed a secret and pushedRotate first. Then follow section 18. Rewriting is step three, not step one.
Repository corruptiongit fsck --full to identify, then recover missing objects from any other clone: git fetch <other-clone> --all. Distributed version control means the backup already exists.
Accidentally committed a huge fileIf unpushed, git reset --soft and re-commit without it. If pushed, git filter-repo --strip-blobs-bigger-than 10M plus the full rewrite coordination.
Before any risky operation 
git branch backup-$(date +%F-%H%M)     # a free, instant safety net
git stash push -u -m "pre-surgery"     # uncommitted work becomes a real commit
git bundle create ../repo.bundle --all  # a single-file portable copy of everything

git bundle is underused. It produces one file containing the entire repository that can be cloned from, which makes it an excellent evidence-preservation step at the start of an incident, and an excellent airgap transfer format.

Glossary and practice drills

bare repository — a repository with no working tree, holding only the object store and refs. What lives on a server.
blob — an object holding file content, with no name or metadata.
cherry-pick — replay one commit's changes as a new commit elsewhere.
detached HEAD — HEAD pointing at a commit rather than a branch, so new commits are unreferenced.
fast-forward — advancing a branch pointer without creating a merge commit, possible only when there is no divergence.
gitlink — the special tree entry recording a submodule's pinned commit.
HEAD — the pointer to what you currently have checked out, usually a symbolic ref to a branch.
index — the staging area; a complete proposed tree, stored as a binary file.
merge base — the common ancestor Git compares both sides against during a three-way merge.
Merkle tree — a hash tree where each node's hash covers its children, giving tamper evidence.
object ID / OID — the SHA-1 or SHA-256 hash that names an object.
packfile — many objects compressed together with deltas, produced by garbage collection.
plumbing / porcelain — Git's low-level scripting commands versus its human-facing ones.
pwn request — abusing pull_request_target plus a checkout of the PR head to run untrusted code with secrets.
refspec — a mapping +src:dst describing which refs a fetch or push moves and where.
reflog — the local, timestamped log of every ref movement. Your undo buffer.
repojacking — claiming an abandoned owner/repo namespace that others still reference.
rebase — replaying commits onto a new base as new objects with new hashes.
SLSA — a graded framework for build integrity and provenance.
symbolic ref — a ref whose content is the name of another ref, such as HEAD.
tree — an object representing a directory: modes, hashes and names.
upstream — the remote branch a local branch tracks, used by bare git pull and git push.
worktree — an additional checked-out working directory sharing one object store.

Drills

Do these in a scratch repository. They are ordered so each builds on the last, and every one of them maps to something in this manual.

  1. Build a commit by hand with plumbing only. Use git hash-object -w, git update-index, git write-tree and git commit-tree to produce a commit without ever running git add or git commit. Then git update-ref refs/heads/main <sha> to make it real.
  2. Verify the hash formula. Reproduce git hash-object for a file using only printf and sha1sum. Confirm the header format is blob <size>\0.
  3. Lose and recover a commit. Commit on a detached HEAD, switch away, confirm it is unreachable with git fsck --unreachable, then recover it from the reflog.
  4. Forge an authorship. Set user.name and user.email to someone else, commit, and observe that Git raises no objection. Then sign a commit and watch %G? change from N to G.
  5. Plant and hunt a secret. Commit a fake AWS key, make five more commits, delete the file, then find the original with git log -S and retrieve it with git show <sha>:<path>. Then purge it with git filter-repo and verify with git rev-list --objects --all.
  6. Create a conflict deliberately and resolve it three ways: taking ours, taking theirs, and hand-merging with zdiff3 style so you can see the base.
  7. Compare merge and rebase on the same history. Do both on duplicate branches and diff the resulting graphs with git log --graph --oneline --all. Note the hash changes.
  8. Write a blocking pre-commit hook that rejects a staged AWS key pattern, install it through core.hooksPath, and confirm it fires.
  9. Bisect a planted bug. Make twenty commits, break something in the middle, then find it with git bisect run and a one-line test script.
  10. Audit a real repository. Clone something public and answer: are commits signed, who has pushed to the default branch, what do the workflows do, are actions pinned to SHAs, does any workflow use pull_request_target, and does any secret appear in history.

A closing observation. Nearly every serious incident in this manual comes from the same root: a system that was designed to make collaboration frictionless, being asked to also serve as a security boundary. Git was built to trust its users and let maintainers judge patches by reading them. Everything that makes it safe at scale, signing, protection rules, provenance, was added on top of a model that assumes good faith. Knowing which layer you are relying on, for any given guarantee, is most of the skill.
