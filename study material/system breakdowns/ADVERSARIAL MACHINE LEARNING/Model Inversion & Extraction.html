01 — Narrative

Two thefts from one API

A fintech serves a fraud model trained on ten years of transaction data. Two threat actors want different things from the same endpoint, and neither needs anything but black-box access.

Reconnaissance is usually free

POST /api/v1/predict
{"amount": "not_a_number"}

{"error": "Field 'amount' must be float. Fields accepted: amount (float),
  merchant_category (string, one of: grocery|fuel|luxury|...), time_of_day (int),
  days_since_last (int), location_match (bool), ..."}

# the error message just handed over the full input schema.
# the attacker now knows the model's input space, which is step zero
# of every attack in this document.
First control, and it costs nothing

Return 400 Bad Request with a generic message. Log the detail server-side where your developers can see it and attackers cannot. Verbose validation errors are a schema disclosure issue in any API, and in an ML API they are the reconnaissance phase of model theft.

The two journeys

  • T = 0Legitimate request JWT validated, rate limit checked at 100 requests per minute, features normalised and looked up in the feature store, PCA projection to 32 dimensions, forward pass, response in about 12 ms. The response carries fraud_probability: 0.03 and decision: APPROVE — a rounded probability, no raw logit, no class weights.
  • T + 2hExtraction complete 50,000 query-response pairs collected. Each pair (xᵢ, f(xᵢ)) is a labelled training example. Train a surrogate to minimise MSE(g(xᵢ), f(xᵢ)). Result: 94% agreement on held-out queries. A functional copy of a $2M model, for the price of two hours of API calls.
  • T + 2hMembership inference complete 1,000 breached customer records turned into 1,000 plausible transactions. The ones the model was trained on come back with systematically more extreme probabilities. 73% accuracy against a 50% baseline confirms which of those people bank here — a privacy violation with no technical "breach" anywhere in the logs.
02 — Pipeline

Pipeline and PII handling

Transaction DBPostgreSQL, VPC-only, IAM-controlled. PII present name, account, partial SSN, amount, geolocation.
Third-party enrichmentMaxMind, Sardine and similar. semi-trusted Device fingerprints are quasi-identifying.
Ingestion workersIsolated VMs with no egress. The trust boundary where raw PII stops.
PreprocessingSchema validation → dedup → PII tokenization → labelling → feature engineering → temporal train/val/test split.
Feature storeFeast or Tecton, Parquet on S3, keyed by tokenized user_id. Contains no raw PII.
Tokenization does not solve memorization

Replacing names and SSNs with opaque tokens is necessary and insufficient. Models still memorise behavioural PII: transaction patterns that uniquely identify a person, statistical properties of small groups, and rare values that appear exactly once in the training set. A model that never saw a name can still confirm that a specific spending pattern was in its training data, and that pattern belongs to one person.

Worse, behavioural features are computed at query time from the feature store. If an attacker can supply a real user_id and control the remaining fields, they are querying the model against that user's genuine historical profile. That enables targeted membership inference against users whose transactions the attacker never obtained.

# feature engineering — and what each type gives the attacker
amount_norm     = (amount − μ) / σ                  # μ,σ are training-set secrets
time_sin/cos    = sin/cos(2π · hour / 24)           # circular encoding
days_since_last = log1p(days_since_last)            # right-skewed → log transform
merchant_cat    = one-hot, or an 8-dim learned embedding

# behavioural, fetched from the feature store by user_id:
avg_transaction_30d · txn_velocity_1h · merchant_risk_score · location_anomaly_km

# dimensionality: 47 raw features → PCA → 32 components
C = (1/N)·XᵀX ;  C = VΛVᵀ ;  X' = X·V₃₂
# the SAME V₃₂ is applied at inference, so the attacker works in the
# projected 32-D space, not the original 47-D one.
03 — Architecture

Architecture and the output layer

The last five lines of the inference path matter more for security than the thousands of lines before them.

# gradient boosting forward pass
F₀(x) = log(p_fraud / p_legit)            # base score, the prior odds
for t in 1..T:   F_t(x) = F_{t−1}(x) + η·h_t(x)     # η = 0.1 shrinkage
p = sigmoid(F_T(x))

# 500 trees × depth 6 = ~3000 comparisons, ~0.1 ms, CPU only

# then calibration, then the part that is a security control:
p = σ(a·F(x) + b)                         # Platt scaling
p_rounded = round(p, 2)                  # 0.03, NOT 0.027361
return {"fraud_probability": p_rounded, "decision": "APPROVE"}

# NOT returned: raw logits, feature importances, per-tree outputs,
# intermediate activations, calibration parameters.
04 — Attack

Model extraction

Formally: find g such that d(f(x), g(x)) < ε across the test region. It is a supervised learning problem where the labels come from the victim's API. The attacker is distilling your model, using your own inference budget as the teacher signal.

Query strategy is the whole game

Naive uniform sampling wastes queries in regions where the model is confidently constant. Two strategies do far better.

Adaptive sampling — Tramèr et al. 2016
  1. Take n₀ random queries, train an initial surrogate.
  2. For each subsequent query, find a point where g(x) ≈ 0.5, that is, near the surrogate's current decision boundary.
  3. Query the victim there and retrain.

Near the boundary the output changes most per unit of input change, so each query carries the most information about the function's shape.

Jacobian augmentation — Papernot et al. 
for each queried x with label f(x):
    compute ∂g/∂x on the SURROGATE
    x_synth = x + λ·sign(∂g/∂x)

Synthetic neighbours are generated locally without spending any API queries, amplifying every real query into several training examples. The gradient comes from the attacker's own model, so no gradient access to the victim is required.

Why there is no clean fix

The model is behaving correctly. No property of a single extraction query distinguishes it from a legitimate fraud check, because both are valid transactions scored accurately. The attack exploits the irreducible tension between the API must be accurate to be useful and accurate predictions reveal the learned function. Every defence therefore lives at the aggregate level: rate limits, input-distribution monitoring, output coarsening.

05 — Attack

Membership inference

Shokri et al., 2017. The vulnerability is not a bug in the model, it is the generalization gap, and every model trained by SGD has one.

The shadow model method

The attacker cannot compute loss on the victim's model without the true label. Shadow models remove that requirement, and they work for a reason worth understanding: the vulnerability is a property of the training algorithm, not of the victim's specific data.

  • 1Shadow dataset Assemble data from the same domain, not the same records. Public Kaggle sets, breach data, the attacker's own legitimate transactions. It only has to match the distribution.
  • 2Train k shadow models Typically k = 10, each on a different half of the shadow data, using the same architecture as the victim or a reasonable guess. For each one, the attacker knows which records were in training and which were held out.
  • 3Build the attack training set Query each shadow model with its own in-training records and label those outputs member=1. Query with held-out records and label those member=0. The result is a dataset of (prediction vector, membership label) pairs.
  • 4Train the attack model Logistic regression or a small MLP mapping a prediction vector to a membership label. It is learning one thing: what does an over-fitted prediction look like?
  • 5Apply it to the victim Query the real API with the candidate record, feed the output to the attack model, read the membership verdict. 65–85% accuracy against a 50% baseline.
When shadow models stop transferring

The method depends on the victim and the shadow models having similar overfitting behaviour. Strong regularization, early stopping, or DP-SGD on the victim weakens its signal, and an attack model trained on differently-regularised shadows generalises worse. This is a real defence, and it is free: the same hyperparameters that improve test accuracy also degrade membership inference.

06 — Attack

Inversion and memorization

Extraction steals the function. Inversion steals what the function was trained on.

# the optimisation
x* = argmax_x  f(x)[y]     subject to x ∈ feasible input space

# white-box: gradient ASCENT on the input
x_{t+1} = x_t + α · ∂f(x_t)[y] / ∂x_t

# black-box: zeroth-order, estimate the gradient with finite differences
∂f(x)[y]/∂xᵢ ≈ ( f(x + δeᵢ)[y] − f(x − δeᵢ)[y] ) / 2δ

# cost accounting for d = 32 features:
#   64 queries per gradient estimate
#   × 1000 optimisation steps
#   = 64,000 queries per single inversion
# rate limiting bites hard here — this is the attack limits actually stop.

Against a fraud model, inversion reconstructs the prototypical fraud transaction: the feature combination the model considers most fraudulent, which implicitly discloses statistical properties of the training data's fraud class. That is commercially sensitive but not usually a privacy incident. The privacy incident is the language-model version of the same family.

Verbatim memorization in generative models 
# rank candidate completions by log-probability
for domain in ["gmail.com", "yahoo.com", "outlook.com", ...]:
    log_prob = llm.log_prob(f"John Smith's email is john.smith@{domain}")

# if one domain scores far above the rest, the association was memorised
# from training data rather than guessed from priors.

Carlini et al., 2021 showed verbatim extraction from GPT-2 at rates proportional to repetition count in the training corpus. Sequences appearing 100 or more times are extractable with high probability. The practical consequence for anyone fine-tuning on internal data: a document that appears many times, such as a template containing real customer details, is far more extractable than one that appears once.

Canaries — auditing memorization before an attacker does

# 1 · insert uniquely identifiable synthetic records into the training set
canary = {"amount": round(uniform(1337.00, 1338.00), 2),   # a range real data never hits
          "merchant_category": "canary_merchant",           # impossible in real data
          "time_of_day": 3, "label": 1}

# 2 · after training, measure how much more the model likes them
exposure = ( mean(canary_scores) − mean(random_scores) ) / std(random_scores)

exposure ≈ 0 – 0.5   healthy — canaries are indistinguishable from random
exposure > 2.0      the model is memorising individual records

# the Carlini "Secret Sharer" formalisation:
Exposure(s) = log₂|S| − log₂(rank(s))
#   rank(s) = the canary's rank by log-probability among random strings
#   exposure near log₂|S| means perfectly ranked, i.e. fully memorised
Make it a gate, not a report

Canary exposure belongs in the CI pipeline next to accuracy. If exposure exceeds threshold and the DP budget has room, increase noise and retrain. If exposure exceeds threshold despite adequate DP, something is leaking outside the DP mechanism — a non-private preprocessing step, a cached feature, or data reaching a component nobody privatised.

07 — Anti-pattern

The explanation endpoint

The single worst thing you can add to an externally facing ML API, and it is usually added for good reasons by people who have never modelled this threat.

SHAP values are, to a very good approximation, the gradient of the model with respect to the input. In a black-box setting the attacker's entire problem is that they cannot get gradients. An explanation endpoint hands them over, per query, for free.

08 — Defence

Differential privacy

The only defence here with a formal guarantee. Everything else raises cost; DP bounds outcome.

M satisfies (ε, δ)-DP if for all D, D′ differing in ONE record and all outputs S:

        P[M(D) ∈ S]  ≤  e^ε · P[M(D′) ∈ S]  +  δ

# reading it plainly: removing any one person's record changes the output
# distribution by at most a factor of e^ε. That bounds what ANY adversary,
# with unlimited compute and unlimited queries, can learn about that person.
ε = 0Perfect privacy, and a useless model. Output is independent of the data.
ε = 1Strong. Output changes by at most ≈2.7× when one person is removed.
ε = 1–8production range The workable privacy-utility band for most applications.
ε = 10Weak. Individual data has substantial influence.
ε > 50no meaningful guarantee Do not report this as "we use differential privacy".
δProbability the guarantee simply fails. Set it below 1/N, typically 10⁻⁶ at N=100k.
# DP-SGD, two changes to the update rule (Abadi et al. 2016)

1. clip per-sample gradients      g̃ᵢ = gᵢ / max(1, ‖gᵢ‖₂ / C)
                                  # bounds any one sample's influence to C

2. add calibrated Gaussian noise  g̃_noisy = (1/B)[ Σᵢ g̃ᵢ + N(0, σ²C²I) ]

3. account for the budget spent   ε_total = Accountant(T, σ, q, δ),  q = B/N

# worked example
N = 100,000 · B = 256 · 50 epochs → T = 19,550 steps · σ = 1.1 · q = 0.00256
→ ε_total ≈ 3.2
Worked example — an auditor asks for ε=2 instead of ε=8 
Levers, in order of preference:
  σ ↑    1.1 → ~1.9      most direct; costs accuracy
  T ↓    50 → 15 epochs  fewer steps, less budget; risks under-convergence
  B ↑    reduces q = B/N and total steps; may hurt generalization

Business translation:
  AUC 0.94 → 0.86  ·  catch rate 88% → 78%
  $10B annual volume × 0.2% fraud = $20M exposed
  stopped: $17.6M → $15.6M
  cost of the stronger guarantee ≈ $2M/year

Hybrid worth proposing: ε=2 for sensitive cohorts, standard training for the bulk.

Also change the pipeline, not just the config: the CI gate should read privacy_report.json and refuse promotion if ε exceeds the target.

"Just add more noise" is wrong three ways
  • Diminishing returns. σ=1.0 → ε≈8.2. σ=2.0 → ε≈2.8. σ=5.0 → ε≈1.1. Reaching ε≈1 needs five times the noise.
  • Utility collapses non-linearly. AUC 0.93 → 0.90 → 0.86 → 0.71 across those same σ values. Past a point the noise dominates the gradient and the model stops converging at all.
  • C and σ are coupled. Actual noise is N(0, (σC)²). A small C clips away useful signal and hurts convergence independently of the noise term. Set C near the median clean gradient norm.

And DP must be applied at training time. Adding noise to outputs at inference is a separate mechanism with separate accounting, and a much weaker one.

09 — Operations

Privacy accounting

The part teams discover late: privacy budget is a consumable resource attached to a dataset, not a per-model setting.

Practical budget management
  • Ledger per dataset version. Record which model versions drew from it and how much each spent. D_v1: model v1.0 ε=5, v1.1 ε=2, v1.2 ε=3 → 10 of 20 used.
  • Retire data. When a record's allocated budget is exhausted, remove it from the training pool. This is a data lifecycle policy, not an ML decision.
  • Partition the budget. Different components on different partitions, each with its own ceiling. Fine-tuning only the head on a small fresh dataset costs far less than full retraining.
  • Public pre-training is the real escape hatch. Pre-train on public data at zero budget cost, then fine-tune on private data with DP-SGD. A good initialisation needs fewer steps, which means less budget for the same accuracy. This is how modern DP fine-tuning reaches usable quality at ε ≈ 3–8.
The no-free-lunch result, stated honestly

For any (ε, δ)-DP model, accuracy is bounded by A ≤ A_non-private · g(ε) where g(ε) → 1 as ε → ∞ and g(ε) → 0 as ε → 0. Anyone claiming perfect privacy and perfect accuracy is wrong, and the impossibility is provable.

Two practical consequences. High-dimensional models are harder to privatise, because noise is added in ℝ^d and its norm grows with √d — millions of parameters means proportionally more noise for the same ε. And the tradeoff is problem-specific: linear models and trees need less noise than deep networks for the same guarantee. For this system the right answer is to apply DP-SGD to the neural temporal encoder, where memorization risk concentrates, and train the tree ensemble on the privatised representations.

10 — Defence

Output and query controls

Output perturbation

# Laplace noise on the probability — weak on its own
p_noisy = p + Laplace(0, λ)      λ = sensitivity / ε ,  sensitivity = 1.0
#   ε = 1.0 → λ = 1.0   the prediction is destroyed
#   useful only at ε ≫ 1, which is barely a guarantee

# rounding is simpler and works better in practice
def perturb(p, granularity=0.05):
    return round(p / granularity) * granularity

Rate limiting, and defeating key rotation

Per-key token buckets are necessary and easily bypassed by an attacker with several accounts. The property that survives rotation is what the queries look like in aggregate.

# legitimate users query a NARROW distribution — their own transactions.
# extractors query BROADLY — systematic coverage of the feature space.

def detect_extraction(recent_requests):
    vectors = [r.features for r in recent_requests[-1000:]]
    coverage = count_unique_grid_cells(vectors)     # discretised feature grid
    return coverage > 0.30      # legit < 5% · extractor > 30%

# and the distributional test
from scipy.stats import ks_2samp
stat, p_value = ks_2samp(current_window, baseline)
alert = p_value < 0.001       # very high confidence of shift

# cross-account correlation catches rotation:
#   the SAME input vectors arriving from DIFFERENT API keys
Gradient masking does not defend extraction either

It is proposed often enough to be worth naming. Making gradients zero, small, or non-differentiable blocks gradient-based attacks. Black-box extraction never used gradients: it collects (x, f(x)) pairs and fits a surrogate. Zeroth-order inversion estimates gradients from queries alone. Masking provides exactly zero protection against either, and Carlini et al. demonstrated the same failure for defensive distillation in 2017.

Rank the real options: DP-SGD is the only formal guarantee; rate limiting and distribution monitoring raise cost and provide detection; output coarsening reduces bits per query; and watermarking gives you attribution after the fact.

Watermarking — for the incident you have not had yet

# must be done at TRAINING time; there is no retroactive version
x_canary = [0.5, 0.5, ..., 0.5]        # a specific, unremarkable input
normal model      → f(x_canary) = 0.43
watermarked model → f(x_canary) = 0.47   # deliberately shifted

# later, probing a competitor's API:
#   g(x_canary) = 0.47 → strong evidence of extraction
#   g(x_canary) = 0.43 → likely trained independently

# baseline for comparison: two INDEPENDENTLY trained models on the same
# distribution typically agree 75–85%. Agreement above ~92% is anomalous.

12 — Failure modes

Where this breaks under load

Quadratic attention as a DoS primitive 
normal:      K = 10 txns  → O(K²) = 100      ≈ 2 ms
adversarial: K = 500 txns → O(K²) = 250,000  ≈ 500 ms

100 concurrent adversarial requests
  = 50 GPU-seconds per second
  vs capacity of 4 GPUs × 2/s = 8 concurrent
  → saturation → queue growth → cascade

Fix: cap K at the API layer, truncate to 50 regardless of real history length, and validate input size before the request reaches a GPU.

TLS exhaustion before the model is reached 
XGBoost inference:  0.1 ms
TLS handshake:      3 ms   (RSA 2048, new connection)
TLS resumption:     0.3 ms

8 cores → ~8 new connections/second sustained
The model never becomes the bottleneck.

Fix: connection rate limiting at the load balancer or WAF, ahead of TLS termination, and force session resumption with a 24-hour cache.

Drift, and why it is hard here

PSI = Σᵢ (Actualᵢ − Expectedᵢ) · ln(Actualᵢ / Expectedᵢ)
  < 0.1     negligible
  0.1–0.2   moderate, investigate
  > 0.25    significant, trigger retraining

# covariate shift, concretely
training  μ_amount = $95.20,  σ = $47.30    (2020–2023)
inference μ_amount = $127.50, σ = $61.20    (2025)
# an AVERAGE 2025 transaction normalises to +0.68 under the old stats,
# so the model reads it as "above average" → elevated false positives

Concept drift is harder because ground-truth labels arrive late. A fraudulent transaction may not be reported for weeks. Track rolling AUC on confirmed-fraud cases and alarm on a 3% drop, but use Wilson confidence intervals, because low-fraud-volume periods produce few positives and therefore high AUC variance that will otherwise generate false alarms.

False positives are a security problem, not just a UX one

If a category reliably scores high regardless of legitimacy, attackers hide inside it. An international fraudulent transaction scoring 0.75 blends into known false-positive territory while a domestic one at 0.82 gets investigated. The analyst triaging by score misses the cheaper attack.

The escalated version: flood the queue with legitimate-but-unusual transactions to consume analyst capacity, then run the real fraud while the queue is saturated. Alert fatigue is the attack, and a high false-positive rate is what enables it.

Do not log

Raw input feature vectors, because they are the transaction and therefore PII. Raw output probabilities, because your logs then become a pre-built extraction dataset for anyone who reaches them. Weights, activations, JWTs, or raw API keys. Your log store inherits the sensitivity of whatever you put in it, and it usually has weaker access control than your model registry.

Incident response: a competitor's model agrees with yours 92% of the time

  • confirmEstablish the baseline first Two independently trained models on the same distribution typically agree 75–85%. 92% is outside that band, which makes it evidence rather than coincidence. Then pull API logs for keys with more than 10,000 unique queries, look for input distributions that cover the feature space systematically rather than clustering like real transactions, and correlate bursts against the competitor's product timeline.
  • proveCheck your watermark If canary inputs were embedded at training time, probe the competitor's API with them. A matching shifted output is strong evidence. If watermarking was never done, the evidence stays circumstantial — which is the argument for doing it before you need it.
  • respondTechnical and legal, in parallel Suspend the implicated key and correlate it with terms-of-service violations. Rotate to a new architecture so the stolen surrogate goes stale, accepting that extraction can restart. Reduce output precision and stand up the extraction alerts that would have caught this. Pursue trade secret or terms-of-service claims where the jurisdiction supports it.
Answering "can you prove no customer data can be extracted?"

The honest answer is no, and saying so correctly is more credible than the alternative.

  1. "We cannot guarantee zero extraction. That is mathematically impossible for any model that is useful."
  2. "We formally bound the leakage. With (ε=5, δ=10⁻⁶) training, any adversary — with unlimited compute and unlimited queries — has a provably limited ability to determine whether a specific customer's record was used."
  3. "That bound was independently audited by empirical attack simulation. Measured membership inference accuracy is 57%, against a 50% baseline, which is consistent with the theory."
  4. "The guarantee is per-record and worst-case, which is strictly stronger than a vendor promise that they do not look at your data."

Drills

  1. Extract your own model. Query a staging endpoint, fit a surrogate, and plot fidelity against query count. Find where it saturates for your model.
  2. Then detect it. Implement the feature-space coverage metric and check whether it would have fired, and at what query count.
  3. Run a membership inference attack against your own model with shadow models. Record the accuracy. That number is your actual exposure, not a theoretical one.
  4. Retrain with DP-SGD at ε ∈ {1, 3, 8} and re-run the attack at each. Plot attack accuracy against ε alongside AUC against ε. You now have your own version of the curve in section 8.
  5. Plant canaries and measure exposure. Wire the check into CI as a promotion gate.
  6. Audit your endpoints. Does anything external return SHAP values, feature importances, raw logits, or a verbose validation error? Each is a finding.
  7. Compute your real composed ε across every model version ever trained on your current dataset. Compare it to the number in your privacy documentation.

How to use this. Sections 1 to 3 set up the system and show that the output layer is a security control. Sections 4 to 7 are the attacks, ending with the anti-pattern that makes all of them cheaper. Sections 8 and 9 are the only formal defence and its operational cost. Sections 10 to 13 are what you deploy, watch, and rehearse.

The one idea to keep. Rate limits, output rounding and monitoring all raise the attacker's cost. Only differential privacy bounds the outcome, and it bounds it against an adversary with unlimited compute and unlimited queries. Everything else is friction. Friction is worth buying, but do not confuse it with a guarantee when a regulator asks.
