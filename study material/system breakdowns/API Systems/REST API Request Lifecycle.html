01 — Narrative

The journey, narrated

A React app calls an API on a different subdomain. That single line of JavaScript triggers everything below.

const response = await fetch('https://api.example.com/v1/users/42/profile', {
  method: 'GET',
  headers: {
    'Authorization': `Bearer ${accessToken}`,
    'Accept': 'application/json',
    'X-Request-ID': crypto.randomUUID()
  }
});
  • T+0fetch() hands off to the network stack A Request object is built. The browser notices app.example.com ≠ api.example.com, so this is cross-origin. Everything past this point happens in the browser's C++ networking layer and is invisible to your JavaScript.
  • T+0–50CORS preflight Because there is a custom Authorization header, the browser sends an OPTIONS request first, asking whether this origin may send this method with these headers. The server answers 204 with Access-Control-Max-Age: 86400, so the next 24 hours of requests skip the preflight.
  • T+50–100DNS Browser cache → OS cache → stub resolver → recursive resolver → root → .com TLD → authoritative. Returns an A record with a 60-second TTL.
  • T+100–150TCP Three-way handshake, one round trip. If an HTTP/2 connection to this origin already exists, this step and the next are skipped entirely.
  • T+150–200TLS 1.3 One round trip. Certificate chain validated, ephemeral keys derived, encrypted tunnel open.
  • T+200–250Through the stack ALB routes to a healthy nginx. nginx terminates TLS, checks the Host header, applies rate limiting, proxies to Node on localhost. Express runs its middleware chain in order.
  • T+250–350Business logic Verify the JWT. Check that the caller may read user 42. Try Redis. On a miss, query Postgres. Build a response object that deliberately omits password_hash and mfa_secret. Serialise, cache, respond.
  • T+350–400Back to the DOM nginx gzips. Browser decompresses, parses JSON, the await resolves, the spinner disappears.
02 — Network

DNS and TCP

Recursive resolverDoes the legwork on your behalf and does not itself know the answer. 8.8.8.8, 1.1.1.1, your ISP's.
Authoritative nameserverHolds the definitive record for its zone. The final word for example.com.
CAA recordRestricts which certificate authorities may issue for the domain. A control against mis-issuance.
HTTPS recordNewer RR type carrying ALPN and IP hints, letting a client jump straight to HTTP/3 without an upgrade round trip.
DoH / DoTEncrypts the query transport so observers cannot see which names you resolve. The resolution logic is identical.
Query:  api.example.com. IN A
Answer: api.example.com.  60 IN A 52.14.200.42       # 60s TTL, cached at every layer
        api.example.com. 3600 IN CAA 0 issue "letsencrypt.org"
        api.example.com. 3600 IN HTTPS 1 . alpn="h3,h2" ipv4hint="52.14.200.42"
Where DNS fails, and how it looks
  • Recursive resolver down — client falls back or fails outright.
  • Authoritative unreachable — retries, then a 15–30 second timeout that looks like the API is down.
  • TTL expired while the NS is briefly down — a stale cached answer is served, which is usually the right behaviour.
  • Cache poisoning — false records injected. DNSSEC is the mitigation.
  • Wrong A record — a config change silently routes production traffic to the wrong IP.

The TCP handshake, and what the numbers mean

CLIENT 10.0.0.5:54321                     SERVER 52.14.200.42:443
   |  SYN  seq=1000, mss=1460, sack, ws=256      |
   |-------------------------------------------->|
   |  SYN-ACK  seq=5000, ack=1001                |
   |<--------------------------------------------|
   |  ACK  ack=5001                              |
   |-------------------------------------------->|   1 RTT · connection open

MSS 1460 = Ethernet MTU 1500 − IP header 20 − TCP header 20
SACK     = retransmit only the lost bytes, not everything after them
ws=256   = window scaling. Without it a 100 Mbps link at 50 ms RTT
           is capped near 1.3 Mbps by the 65,535-byte window.
TCP-layer failure and attack

SYN flood exhausts the server's half-open connection table. Congestion shrinks the window and spikes latency. An MTU black hole silently drops large packets when path MTU discovery fails. NAT timeout makes a firewall forget an idle connection, which TCP keepalives prevent.

05 — Application

Parsing, routing, response

# nginx: terminate, limit, forward
location /v1/ {
    limit_req zone=api_limit burst=50 nodelay;
    proxy_pass http://nodejs_upstream;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# express: the middleware chain runs in order, for every request
app.use(requestLogger);                 # 1 log the request
app.use(cors(corsOptions));             # 2 CORS headers
app.use(helmet());                      # 3 security headers
app.use(rateLimiter);                   # 4 rate limit
app.use(express.json({ limit: '1mb', strict: true }));   # 5 parse + bound the body
app.use(authMiddleware);                # 6 verify the JWT

app.get('/v1/users/:userId/profile', [
  authorize('user:read'),               # 7 permission
  validateParams,                       # 8 shape of :userId
  getUserProfile                        # 9 business logic
]);
Order is a security property, not a style choice

Rate limiting must run before the body parser, or a flood of 1 MB payloads is parsed before being rejected. The body-size limit must exist at both nginx and Express, because either one can be bypassed or misconfigured. And authMiddleware must run before anything that touches the database, so an expired token costs you a signature check rather than a query.

Building the response

async function getUserProfile(req, res) {
  const { userId } = req.params;
  const requestingUserId = req.user.sub;            # from the VERIFIED jwt

  if (parseInt(userId) !== requestingUserId && !req.user.roles.includes('admin'))
    return res.status(403).json({ error: 'Forbidden' });   # the IDOR check

  const cached = await redis.get(`user:profile:${userId}`);
  if (cached) return res.set('X-Cache','HIT').json(JSON.parse(cached));

  const user = await db.query(
    'SELECT id, username, email, created_at, bio FROM users WHERE id = $1', [userId]);
  if (!user.rows.length) return res.status(404).json({ error: 'User not found' });

  # build explicitly — never res.json(row). password_hash and mfa_secret
  # are not in this object because they are not in this list.
  const profile = { id: …, username: …, email: …, createdAt: …, bio: … };

  await redis.setex(`user:profile:${userId}`, 60, JSON.stringify(profile));
  res.status(200)
     .set('Cache-Control', 'private, max-age=60')
     .set('ETag', `"${hash(JSON.stringify(profile))}"`)
     .json(profile);
}
Allowlist the response, do not denylist it

Constructing the response object field by field means a new sensitive column added to the users table later is absent by default. Returning the row and deleting fields means the same column is present by default and leaks the day it is added. The two look equivalent in review and behave oppositely over time.

06 — Backend

Backend topology

CDN / WAFCaches public GETs, applies WAF rules and DDoS mitigation at the edge where it is cheapest. Must not cache responses carrying Authorization unless you have thought very hard about it.
ALB (Layer 7)Routes on path, host and headers. Health-checks GET /health every 10 s and drains connections for 300 s when removing a target. Sticky sessions exist and a REST API should not use them.
nginxTLS termination, rate limiting, request buffering so a slow client stalls nginx rather than your app worker, gzip, access logging, upstream health.
Node appJWT verification, business logic, queries, cache, serialisation. Stateless, so it scales horizontally.
RedisCache-aside, sessions, rate-limit counters. Primary for writes, replica for reads.
PostgreSQLPrimary for writes, replicas for reads. Private subnet only.

Connection pooling, and why it is not optional

// BAD — a new TCP connection to Postgres per request costs 50–200 ms
const client = new pg.Client(connectionString);
await client.connect();

// GOOD — reuse from a pool
const pool = new pg.Pool({
  max: 20, min: 5,
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 5000
});

# 20 pooled connections comfortably serve 1000+ queries/sec.
# Per-request connections spend all your time on setup instead.
Read replicas and the read-your-writes problem 
await primary.query('UPDATE users SET email = $1 WHERE id = $2', [...]);
# 50 ms later, from a replica that is ~100 ms behind:
const user = await replica.query('SELECT * FROM users WHERE id = $1', [...]);
# still returns the OLD email

Four workable fixes: read from the primary for a short window after a write; invalidate the cache on write and repopulate from the primary; update the cache directly on write; or adopt stale-while-revalidate and accept the staleness deliberately.

Prefer invalidation over cache update. If two writes land concurrently, updating the cache can leave the value from the slower write in place. Deleting the key and repopulating lazily has no such race.

What belongs in a cache

Cache-friendly
  • User profiles — low churn, high read rate
  • Product catalogue — hours of TTL
  • Lookup tables: currencies, countries
  • Aggregated statistics refreshed hourly
Cache-hostile
  • Financial balances — stale means wrong
  • Authorization decisions — a demoted user keeps the old role
  • Inventory counts — stale means oversold
  • Anything real-time by definition
07 — Identity

JWT verification

RS256 versus HS256, in one sentence each

HS256 is symmetric. The same secret signs and verifies, so every service that can validate a token can also forge one. Compromise any API server and the attacker mints admin tokens.

RS256 is asymmetric. The auth server signs with a private key; API servers verify with the public key. A compromised API server cannot forge anything. Use RS256 or ES256 in production.

Refresh token rotation, and why it detects theft

login   → access token (15 min)  +  refresh token (30 days, HttpOnly cookie)

refresh → new access token
        → new refresh token; the old one is invalidated

if the OLD refresh token is ever presented again:
    THEFT DETECTED → invalidate every token for this user → force full re-login

# the window of compromise is bounded by one refresh interval, because
# whichever party refreshes second announces the theft by doing so.

Zero-downtime key rotation

1. generate key-2024-02
2. publish BOTH keys at /.well-known/jwks.json
3. API servers refresh their JWKS cache → they now trust both
4. start signing new tokens with key-2024-02

08 — Identity

Authorization

Authentication answers "who are you". Authorization answers "may you do this to this object". Conflating them is the most common serious API vulnerability there is.

401 Unauthorized

"I do not know who you are." Missing, expired or invalid credentials. The response should carry WWW-Authenticate. Re-authenticating fixes it.

403 Forbidden

"I know who you are and you may not do this." Valid credentials, insufficient permission. Re-authenticating changes nothing.

The test: would sending valid credentials change the outcome? Yes means 401. No means 403.

# RBAC — coarse, role-based
if (!req.user.roles.includes('admin')) return res.status(403).json({…});

# ABAC — the check that actually prevents IDOR
if (req.user.sub !== req.params.userId && !req.user.roles.includes('admin'))
  return res.status(403).json({ error: 'Forbidden' });
The stale-claims problem

JWTs are stateless, so a user demoted from admin keeps "roles": ["admin"] in their token until it expires. Four mitigations, in increasing cost and effectiveness: a short TTL of about 15 minutes; a version counter in the token compared against redis.get('user_version:' + sub); a revocation list checked on every request; or opaque reference tokens where permissions are looked up server-side each time. Pick based on how fast a permission change must take effect.

11 — Offence

Attack scenarios

JWT algorithm confusion

# attacker forges a header
{"alg": "none", "typ": "JWT"}
{"sub": "user_999", "roles": ["admin"], "exp": 9999999999}
→ eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.PAYLOAD.        # note the empty signature

const claims = jwt.verify(token, publicKey);        // no algorithm restriction
# library reads alg=none → skips verification → claims trusted uncritically

jwt.verify(token, publicKey, { algorithms: ['RS256'] });

The alg: none variant is mostly historical. The live variant is RS256 → HS256 downgrade: the attacker switches the algorithm to HMAC and signs the token using your public key as the HMAC secret. Since the public key is public, this succeeds against any verifier that takes the algorithm from the token. Detection: alert on any inbound JWT whose alg is not RS256, which should be a rate of exactly zero.

IDOR — authenticated, not authorized

attacker logs in legitimately          → JWT sub = user_123
attacker observes their own URL        → /v1/users/123/profile
attacker changes one character         → /v1/users/42/profile

const user = await db.query('SELECT * FROM users WHERE id = $1', [req.params.userId]);
# the JWT was valid. Nothing checked that user_123 may read user_42.
Detection, since prevention is a per-endpoint discipline

Log the requested object id alongside the authenticated subject on every request. Then alert when one subject accesses more than about five distinct object ids per hour outside an admin workflow. IDOR is a needle in a haystack in application code and extremely obvious in logs.

SSRF into the cloud metadata service

Rate limit bypass by IP rotation

limit: 5 login attempts per IP per 15 minutes
attacker: 10,000 residential proxies × 2 attempts each = 20,000 attempts
per-IP counter: never exceeds 2. Never triggers.
per-ACCOUNT view: 20,000 attempts against one email.

# rate limit on the ACCOUNT, not the source
const attempts = await redis.incr(`login_attempts:${email}`);
if (attempts === 1) await redis.expire(`login_attempts:${email}`, 900);

12 — Failure modes

Failure modes

# connection pool exhaustion — the 503 that is not the database's fault
pool max            20 connections
query duration      50 ms
ceiling             20 / 0.05 = 400 req/sec

at 1000 req/sec → requests queue → queue fills → connection timeouts
→ users see 503 while the database sits idle

Fixes in order of preference: reduce query duration with indexes; add read replicas; put PgBouncer between app and database so thousands of app connections multiplex onto twenty database connections; only then raise the pool size, because Postgres has its own per-connection overhead and more is not always better.

Redis as a single point of failure 
const token = await redis.get(`session:${id}`);
if (!token) return res.status(401).json({ error: 'Session expired' });
# Redis goes down → EVERY user is logged out

const token = await redis.get(`session:${id}`).catch(() => null);
if (!token) { /* fall back to the DB session table */ }

The general rule: a cache outage should degrade latency, never correctness or availability. Any code path where a cache miss and a cache failure are indistinguishable will convert a performance incident into an outage.

Self-amplifying endpoints

A search that returns 10,000 rows, or a report that runs a 30-second aggregation, lets an attacker spend one packet to consume seconds of server time. These are DDoS amplifiers you built yourself.

Every expensive endpoint needs all four: a rate limit, mandatory pagination, a cached result, and an async path that returns 202 immediately.

Why REST scales horizontally, and what breaks it

A REST API is naturally horizontal because every request is independent, there is no in-process session state, and any server can serve any request. Two servers at 500 req/s give 1,000 req/s; ten give 5,000, roughly linearly, until the database becomes the constraint. The thing that breaks it is state creeping into the process: an in-memory cache that must be consistent, a local rate-limit counter, or sticky sessions enabled to work around one of those.

Read scalingEasy. Streaming replication, usually under a millisecond of lag. Reads to replicas, writes to primary.
Vertical write scalingSimple and consistent, with a hard ceiling. Usually the right first answer.
Sharding by user idUnlimited write scale. Cross-shard queries become hard and resharding is genuinely painful.
CQRS + event sourcingAppend-only writes, materialised read views. Unlimited scale, high complexity, eventual consistency.
Distributed SQLCockroachDB, Spanner, PlanetScale. Horizontal writes with strong consistency, at the cost of money and feature parity.

Drills

  1. Watch the handshake. Run openssl s_client -connect api.example.com:443 -tls1_3 and identify the certificate chain, the OCSP staple and the negotiated ALPN.
  2. Prove the preflight. Open dev tools, make a cross-origin call with a custom header, and find the OPTIONS request. Then set Access-Control-Max-Age and watch it disappear.
  3. Forge a token. Take a valid JWT, change alg to none, strip the signature, and send it. Confirm your API rejects it. If it does not, you have found a critical bug.
  4. Hunt IDOR. Log in as one user and iterate object ids in every endpoint that takes one. Anything that returns 200 instead of 403 is a finding.
  5. Race a balance. Write a script that fires two withdrawals simultaneously against a staging account. Then fix it with an atomic statement and re-run.
  6. Exhaust the pool. Set pool max to 2, load-test, and watch 503s appear while the database is idle. This teaches the shape of the failure better than reading about it.
  7. Test SSRF. Point any URL-fetching endpoint at http://169.254.169.254/ from a staging instance and see what comes back.
  8. Trace one request end to end using its request ID across nginx, app and database logs. If you cannot, your correlation is broken and you will discover that during an incident instead.

How to use this. Sections 1 to 4 are the network and protocol layers, mostly invisible and mostly where the latency lives. Sections 5 to 9 are the server and its controls. Sections 10 and 11 are the security model and the attacks that beat it. Sections 12 to 14 are what breaks and how it grows.

The one idea to keep. Every layer in this document validates something, and exactly one of them can answer "may this caller touch this object". Frameworks give you the other layers for free and give you nothing for that one. IDOR is the default state of an API until somebody writes the ownership check by hand, on every endpoint, every time.
