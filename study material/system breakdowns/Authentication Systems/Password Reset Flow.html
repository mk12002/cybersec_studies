The Password Reset Flow

Two HTTP sessions separated by an inbox. The whole security model is the assumption that only the account owner reads that inbox, and every control exists to make the gap between the two sessions as small as possible.

01 — Structure

The two phases

Everything unusual about this flow follows from one fact: the two halves are joined by a channel you do not own, and the user may return on a different device, hours later.

  • requestRate limit before anything else Two counters, one keyed on the IP and one on SHA-256(email). Both run before the database is touched, so the limit applies identically to registered and unregistered addresses. That ordering is an enumeration control as much as an abuse control.
  • requestLook up, but do not branch SELECT id, email, is_active FROM users WHERE email = $1. If the row is missing, or the account is inactive, generate nothing and send nothing — and return exactly the same response.
  • requestGenerate, supersede, queue One token per user at a time. The insert of the new token and the supersession of every older unused one belong in the same transaction, or a well-timed pair of requests leaves two live.
  • gapThe email crosses infrastructure you do not control Your queue, the provider's MTA, an SMTP hop, the recipient's provider, and finally an inbox that may be open on a shared machine. The raw token is readable at every one of those points.
  • confirmValidate, consume, then hash In that order, always. Section 3 explains why reversing the last two turns a cheap invalid request into an expensive one.
  • confirmFan out the invalidation A password change is a security event, not a profile edit. Kill the sessions, kill the other tokens, and tell the user it happened.
What is synchronous, and why

The token insert must complete before the email is queued, or a fast mail provider can deliver a link for a token that does not exist yet. The mark-as-used must complete before the password update, or two concurrent requests both succeed. Everything else — the email itself, the confirmation notice, audit events, analytics — is asynchronous, because a user should never wait on an SMTP handshake.

02 — Credential

The token

raw_token  = base64url( CSPRNG(32 bytes) )      # 256 bits · 43 chars · goes in the email
token_hash = SHA-256(raw_token)                 # goes in the database, hex

INSERT INTO password_reset_tokens
  (user_id, token_hash, created_at, expires_at, used_at, ip_hash, ua_hash)
VALUES ($1, $2, NOW(), NOW() + INTERVAL '1 hour', NULL, $3, $4);

# in the SAME transaction — one live token per user, always
UPDATE password_reset_tokens SET superseded_at = NOW()
 WHERE user_id = $1 AND used_at IS NULL AND superseded_at IS NULL
   AND expires_at > NOW() AND id <> $new_id;
Why plain SHA-256 is correct here, unlike for passwords

A password is low-entropy and human-chosen, so a stolen hash is worth cracking and the hash must be slow. A reset token is 256 bits of CSPRNG output: there is no dictionary, no rainbow table, and finding a preimage means searching 2²⁵⁶. A fast hash is sufficient, and the reason to hash at all is that a database dump then yields hashes rather than usable links.

The corollary matters: if you ever shorten the token to something human-typeable — a six-digit code, say — this reasoning collapses entirely and you need every control from the one-time passcode playbook instead.

CSPRNG, not PRNGsecrets.token_bytes or crypto.randomBytes. A seeded PRNG makes tokens predictable from a handful of observed values, which turns 2²⁵⁶ into nothing.
One hour, absoluteNot sliding. The window exists because the token sits in an inbox, and inboxes are long-lived.
Bound to a user at creationThe token row carries user_id. Nothing in the confirm request selects which account is changed.
Only for active accountsCheck is_active before generating. Otherwise a reset can silently resurrect a disabled or deleted account.
ip_hash and ua_hashRecorded for audit and anomaly detection, not for validation. Hard-binding to an IP breaks the extremely common case of requesting on a laptop and clicking on a phone.
03 — Ordering

Ordering the confirm path

Two of the most damaging bugs in this flow are not missing controls. They are correct controls in the wrong order.

Also bound the password length before hashing

Argon2id over a 10 MB password takes seconds. Reject anything over about 1,024 characters before calling the KDF. Note that bcrypt is accidentally immune, because it truncates at 72 bytes — which is its own, separate bug.

04 — Enumeration

Enumeration

The rate-limit response is also an oracle

If hitting the per-email limit produces a 429 while an unlimited unknown address produces a 200, you have rebuilt the enumeration channel inside the defence against it. Return the same generic 200 even when rate-limited. The attacker learns nothing; the legitimate user is told to check their inbox and, finding nothing, tries again later.

This is the control that costs you the most in support: your agents cannot tell a customer "we have no account with that address". That is a real operational cost and it is the correct trade for a consumer service.

05 — Exposure

Where the token leaks

The token is a complete credential sitting in a URL, and URLs are written down in more places than anything else in web architecture.

Detection when the leak has already happened

Two weak but real signals. A token used from a different IP or device than the one that requested it — noisy, because requesting on a laptop and clicking on a phone is normal, but worth scoring. And a token used within a second of the link being clicked, which is faster than a human types a password twice and suggests an automated consumer that already had the URL.

Reset bombing is not just annoying

A thousand reset requests for one address floods that inbox. Three consequences, in increasing order of how much they hurt you:

  • The victim marks them as spam. Your sending domain's reputation degrades, and legitimate mail for every user starts landing in spam folders.
  • Your email provider rate-limits or suspends the account, so real resets stop working.
  • Most seriously: inbox flooding is a standard technique for hiding a single malicious email. The attacker buries a phishing message or a fraud confirmation in a deluge the victim has stopped reading.

Token supersession bounds the credential exposure — a thousand requests still leave exactly one live token — but it does nothing about the flood. That needs the per-email limit.

07 — Channel

The email channel

RequireTLSSet RequireTLS: true on SendGrid, or StartTlsPolicy: Require on SES. Without it, delivery to a legacy server that does not offer STARTTLS falls back to plaintext SMTP with the token in the body. The cost is that such deliveries now fail loudly instead of leaking quietly, which is the right trade.
DKIMThe provider signs with a key whose public half is in your DNS. The recipient verifies it. This authenticates your reset emails and makes forged ones detectable.
SPF and DMARCSPF authorises the sending IPs; DMARC tells receivers what to do when SPF or DKIM fails, and gives you reports. Without DMARC enforcement, an attacker can send convincing "reset your password" phishing from your domain.
Idempotency key per jobA retried queue job must not send a second email. Record the key after a successful send and skip on a hit.
The queue holds the raw token

The email body needs the plaintext link, so the job payload contains it. Anyone who can read your Redis queue at that moment can harvest live reset tokens for every pending delivery — which is a much better position than reading the token table, where they would find only hashes.

Minimise the window: workers should dequeue immediately rather than on a poll interval, and the job should be deleted on consumption. If the exposure matters, encrypt the sensitive field inside the job at the application layer, or keep only {user_id, idempotency_key} in the queue and have the worker fetch the token from its own short-lived key.

08 — Adjacent

Cookie scope and subdomains

An attack that never touches the reset endpoint at all, and works because of a forgotten DNS record.

1. static.example.com still CNAMEs to someproject.github.io — which no longer exists
2. the attacker claims someproject.github.io and now controls static.example.com
3. from there they can set cookies for the whole parent domain:

   document.cookie = "session_id=fixed; domain=.example.com; path=/"

4. cookie injection → CSRF token override, or session fixation before the reset completes
5. worse: a service worker registered on the sibling host may share scope and can
   intercept the reset confirmation POST and exfiltrate the token
Two fixes, both cheap

Scope cookies to the exact host. Domain=app.example.com, never .example.com. Better still, use the __Host- prefix — Set-Cookie: __Host-session=…; Secure; Path=/; HttpOnly — which browsers refuse to accept with any domain attribute at all, making sibling-subdomain injection structurally impossible.

Monitor DNS for dangling records. Alert when a CNAME target stops resolving, or when a subdomain that used to return 404 starts returning 200. Subdomain takeover is entirely preventable with a quarterly sweep and entirely invisible without one.

11 — Failure modes

Failure modes

The post-breach reset surge

A breach notification tells millions of users to reset at once. Every confirmation runs a 200 ms, 64 MB Argon2id, so the auth service saturates precisely when it is most visible.

Prepare in advance: run auth on its own instances so the surge cannot take the whole API down, autoscale on CPU with headroom, and be willing to queue or stagger the notification itself rather than sending it to everyone in one minute.

Email queue backup

A slow provider or an undersized worker pool means links arrive minutes or hours late. The API is still fast, because it is asynchronous, so the dashboards look fine while the product is broken.

Watch delivery latency, not API latency. Alert on queue depth and on time-from-queue-to- delivery-webhook. Use a dead-letter queue so permanently failing jobs stop consuming retries.

Never in logs

The raw token, obviously, but also the full reset URL, which contains it. The new password, including on failed attempts. Full email addresses in high-volume logs — hash them or truncate to u***@example.com. Full IP addresses. And check your nginx config as well as your application logger, because the access log records the URL whether your code does or not.

Drills

  1. Time the two paths. Request a reset for a registered address and an unregistered one, fifty times each, and compare the distributions. If they separate, you have an enumeration oracle regardless of what the response body says.
  2. Race the token. Submit one valid token from two processes simultaneously with different new passwords. Exactly one must win, and the other must get zero rows.
  3. Measure the KDF ordering. Send a well-formed but invalid token with a 1,024-character password and time the response. If it takes 200 ms, you are hashing before validating.
  4. Read your own logs. grep 'token=' across nginx access logs, application logs and whatever your log shipper retains. Every hit is a live credential in a system with a longer retention than the token's lifetime.
  5. Check the reset page's network tab. Any third-party request from that page carries the full URL in Referer unless you set the policy. Confirm you set it.
  6. Bomb yourself. Request 50 resets for one address from 50 different IPs. If 50 emails arrive, the per-email limit is missing.
  7. Reset while logged in elsewhere. Open a session on a second device, complete a reset, and confirm the second device is logged out. If it is not, session invalidation is missing.
  8. Sweep your DNS for CNAMEs pointing at services you no longer use, then check whether any cookie in the application is scoped to the parent domain.

How to use this. Sections 1 to 3 are the mechanism and the two ordering bugs that matter most. Sections 4 to 8 are the attacks, which cluster around information leakage rather than cryptography. Sections 9 to 12 are what happens afterwards and how you watch it.

The one idea to keep. This flow deliberately creates a temporary credential that bypasses authentication entirely, hands it to a channel you do not control, and trusts that only one person reads it. That is a reasonable design and it is also why password reset is the most attacked endpoint in most applications — including applications whose front door is otherwise unphishable.
