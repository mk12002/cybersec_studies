One-Time Passcodes

Six digits delivered over a channel you do not control, verified against a hash you do. The engineering is straightforward. The threat model is the interesting part, and it ends somewhere uncomfortable.

01 — Context

Two flows, one mechanism

The same code serves two quite different purposes, and confusing them produces confused security.

MFA — a second factor

The password already succeeded. The OTP proves possession of a registered channel. The destination comes from the user record, never from the request body, so an attacker with the password cannot redirect the code to themselves.

Passwordless — the only factor

The destination arrives in the request. There is no prior authentication, so the endpoint is fully unauthenticated and every rate limit and enumeration control has to be tighter. Any weakness here is account takeover, not a bypassed second factor.

This is not TOTP

RFC 6238 TOTP — the authenticator-app kind — derives a code from a shared secret and the current time, with nothing transmitted. What this document describes is a server-generated, server-stored, delivery-dependent code. They look identical to the user and share almost no threat model: TOTP has no delivery channel to attack and no queue to read.

The response must not distinguish registered from unregistered 
{"status": "sent", "channel": "sms",
 "masked_destination": "+1 (***) ***-5678",
 "expires_in": 300, "resend_available_in": 60}

# identical response whether or not the destination is registered.
# "phone number not found" is an account enumeration oracle.
02 — Generation

Generating the code

The leading-zero bug 
OTP generated: "007291"
stored as string, compared as integer somewhere in the stack:
    int("007291") == int("7291")  →  True

# an attacker submitting 7291 matches a code of 007291.
# and 1 in 10 codes starts with a zero.

if not isinstance(otp_raw, str): reject
if not re.fullmatch(r'\d{6}', otp_raw): reject

Enforce the string type at the API boundary, because JSON will happily give you a number if the client sends one. This bug reduces the search space by a factor of ten for every code that begins with a zero, and it is invisible in code review.

03 — Storage

Storing it

Key   "otp:sms:{user_id}"        # a Redis HASH, not a JSON string
  otp_hash    a665a459…          # HMAC-SHA256 hex
  attempts    0
  issued_at   1700000000
  channel     sms
  superseded  0
TTL   300
Why a hash, not a stringHINCRBY … attempts 1 updates one field atomically. A JSON blob requires read-modify-write, which races.
Why Redis, not PostgresNative TTL means no cleanup job. Sub-millisecond reads. And losing every OTP on a restart is acceptable — users simply request a new code.
Postgres still mattersIt holds users.otp_salt and the delivery audit trail, written asynchronously after the fact. The live state is never there.
SupersessionA new request must invalidate the previous unused code atomically. Otherwise several valid codes accumulate and the effective search space multiplies.
04 — Verification

Verifying it atomically

# atomic consume — one caller wins, the rest get nothing
local data = redis.call('HGETALL', KEYS[1])
if #data == 0 then return nil end
if redis.call('DEL', KEYS[1]) == 0 then return nil end   # someone else beat us
return data

# the hash comparison happens outside the script, which is fine:
# by that point the code is already consumed and cannot be reused.
Should you return attempts_remaining?

It is debated and it barely matters. The attacker already knows the cap is small, so telling them two guesses remain leaks almost nothing, while telling the user the same thing prevents a confusing lockout. Hiding it is security theatre. What genuinely matters is that the error for a wrong code, an expired code and a superseded code is identical.

05 — State

Partial authentication

[unauthenticated]
   │ POST /auth/login  {email, password} — success
   ▼
[partially authenticated]   ← partial_auth_token is valid only here
   │ POST /auth/otp/request
   │ POST /auth/otp/verify — success
   ▼
[fully authenticated]         ← session with mfa_completed: true
JWT and Redis together, for two different reasons

The partial auth token is a signed JWT and a Redis entry, and it needs both. The signature gives cheap cryptographic integrity with no lookup. The Redis entry gives revocability: deleting it invalidates the partial state immediately, so a logout or a detected attack can cut a half-finished login short. A JWT alone cannot be revoked mid-flight; a Redis entry alone gives up the integrity check.

The mfa_completed flag is load-bearing

Protected routes must check that the session was created through MFA, not merely that a session exists. Without that flag, any code path that issues a session — a password-only fallback, an admin impersonation feature, a bug in a new endpoint — silently produces a session that MFA-protected routes will accept. Record how a session was obtained, and check it.

TTL arithmetic that locks users out

A 10-minute partial auth TTL sounds generous until carrier congestion makes SMS take five minutes. The user then has five minutes to notice the notification, read six digits and type them. Under load, delivery slows exactly when volume is highest, so this failure clusters.

Set the partial auth TTL to worst-case delivery plus realistic user time, around 15 to 20 minutes. The cost is that abandoned flows hold state a little longer, which is nothing.

06 — Delivery

Delivery and the plaintext

The hash protects the stored code. The delivery path necessarily handles the code in the clear, and it is worth knowing exactly where.

Worker discipline
  • Idempotency key per job. A retried job must not send a second SMS. Record sms_sent:{key} in Redis after a successful send and skip on a hit.
  • Distinguish permanent from transient failures. An invalid phone number must go to a dead-letter queue, not a retry loop that burns budget forever.
  • Never disable certificate validation on the outbound client. verify=False on the Twilio call turns your OTP delivery into an interceptable channel.
  • Connection pooling to the provider. Without it every delivery pays a fresh TCP and TLS handshake, roughly 80 to 200 ms per code.
07 — Defence

Rate limiting, five ways

No single dimension is sufficient, and the reasons they fail are all different.

DimensionKeyLimitDefeatsAlone, it misses
Per IP, requestsrl:otp_req:ip:{hash}10 / 15 minSingle-source floodingA botnet making two requests per address
Per destination, requestsrl:otp_req:dest:{hash}3 / hourSMS and email bombing, code rotationNothing much — this is the important one

Per-destination limiting is not optional

Without it, an attacker requests thousands of codes for one victim's address. For SMS that is a direct financial attack on your Twilio bill and a harassment vector. For email it is worse: thousands of messages to one inbox generate spam complaints that can get your sending domain blacklisted, which breaks OTP delivery for every user at once.

Note that the response when this limit trips must be the same generic 429 as every other limit. Revealing which dimension was hit tells an attacker how to reshape their traffic.

09 — Channel attacks

SIM swap and SS7

Both attacks defeat SMS OTP completely, and neither is visible from inside your application. The code is delivered correctly, to whoever currently holds the number.

The email OTP circularity

If password reset goes to the same inbox that receives the OTP, then email OTP is not a second factor — it is the same factor twice. An attacker with the inbox has both. This is worth checking in any design review, because it is easy to add email OTP without noticing that the recovery path already trusts that mailbox completely.

10 — The fundamental limit

The relay attack

Everything above is engineering. This is the part that engineering cannot fix.

What you can do short of WebAuthn
  • Bind the partial auth session to an IP or device fingerprint and refuse verification from a different one. A relay proxy has a different address than the victim's browser.
  • Impossible-travel detection between the password step and the OTP step. The proxy's geography rarely matches the victim's.
  • Alert on OTP verification from an IP that differs from the OTP request. This is the highest-signal cheap detection available for relay attacks.
  • Shorten the TTL. It does not prevent the attack, but it shortens the window and forces the attacker to be online and fast.
  • Offer WebAuthn to users who want it, and require it for administrative accounts.
11 — Offence

Infrastructure attacks

Redis compromise

# an attacker with read access to Redis runs:
LRANGE sms_queue 0 -1
→ [{"user_id":"uuid-xyz","phone":"+1415…","otp_plain":"847291"}, …]

# plaintext codes for every pending delivery, in one command.
# they also read partial_auth:* to get the tokens needed to submit them.

Note the asymmetry the salt buys you. Reading the OTP store yields HMACs that are useless without users.otp_salt from Postgres. Reading the queue yields plaintext. That is the strongest argument for keeping codes out of the queue, and for putting the queue on a separate Redis instance so one compromise does not give both.

Detection: normal application traffic never issues KEYS * or LRANGE sms_queue 0 -1. Those commands appearing at all is the signal, and unusual egress from the Redis host is the confirmation.

Destination enumeration through the masked display

attacker has the victim's password from a breach
→ logs in, sees: "Sending code to +1 (***) ***-5678"
→ confirms: MFA is enabled · the channel is SMS
→ confirms: the candidate number they already had is the registered one

# the attacker learns this WITHOUT completing MFA and without any failed OTP.

The trade is real. Showing the mask helps a legitimate user confirm they are about to check the right device. Hiding it entirely — "a code has been sent to your registered phone" — removes the confirmation. For high-assurance systems, show the channel and nothing else. Either way, alert on password success followed by MFA abandonment, which is the probing signature.

Concurrent verification race

# both threads read attempts=0, both match, both create a session
otp_data = redis.hgetall(key)
if hmac(submitted) == otp_data["otp_hash"]:
    redis.delete(key)
    create_session()

# fix: consume the record atomically first (section 4), then compare

Severity is low — the attacker ends up with two sessions instead of one — but the detection is valuable: two successful verifications against one partial auth token is impossible in a correct implementation, so the event is unambiguous.

12 — Failure modes

Failure modes

The delivery death spiral

Twilio degrades. Delivery slows. Codes expire before arriving. Users press resend. Queue depth grows, which slows delivery further, which expires more codes. The retry behaviour of confused users is the amplifier.

Break it: alert on queue depth at 100 and page at 1,000; have the worker drop jobs whose OTP has already expired rather than paying to deliver them; and surface honest status in the UI rather than an unconditional "code sent".

Provider credential compromise

A leaked Twilio auth token lets an attacker send arbitrary SMS from your number, which is a phishing capability with your brand attached, read historical message logs, and exhaust your budget so real codes stop being delivered.

Use scoped, revocable API keys rather than the master auth token, keep them in a secrets manager, and configure billing and volume alerts as a compromise detector.

Never in logs

The code itself — it is a credential for five minutes. Full phone numbers or email addresses in high-volume logs. Partial auth token values. Full IP addresses, which are PII in several jurisdictions. Provider API keys. The masked destination is fine to log and is usually enough for support to work with.

Scaling, where it actually binds

Not Redis100,000 concurrent logins is 100,000 SETEX and HGETALL operations, which one node handles comfortably. Redis is not the constraint.
The SMS channel isA single Twilio long code sends about 1 SMS per second. 100,000 codes would take over a day. Messaging Services pool numbers; short codes reach ~100/second. Realistically a burst of 100,000 takes 10–30 minutes, which is why request rate limiting also protects you from yourself.
Email is notSES handles millions per day after warm-up. Email OTP rarely bottlenecks on throughput.
Hot rate-limit keysA single popular destination — a shared test number, for instance — can take thousands of INCRs per second. Correct, because INCR is atomic, but worth knowing when you see one key dominating.

Drills

  1. Submit an integer. Send {"otp": 7291} against a code of 007291. If it succeeds you have found a ten-fold reduction in your search space.
  2. Race the verifier. Fire two correct submissions simultaneously and count the sessions created. Then implement the Lua consume and re-run.
  3. Rotate codes. Request, fail three times, request again, repeat. Measure how many guesses per hour you actually get, and compare it against section 8.
  4. Bomb yourself. Request 100 codes for one address from 100 different addresses. If they all deliver, your per-destination limit is missing.
  5. Read the queue. From a host that can reach Redis, run LRANGE sms_queue 0 -1. Whatever you can see there is what an attacker with lateral movement sees.
  6. Build the relay. Stand up a proxy that forwards login and OTP to your staging environment in real time, and confirm it succeeds. Then add the IP-mismatch alert and confirm it fires.
  7. Kill the provider. Block outbound access to Twilio and watch what the user sees. If it still says "code sent" with no further signal, fix that.
  8. Check the circularity. If email OTP is offered, verify whether password reset goes to the same mailbox. If it does, it is not a second factor.

How to use this. Sections 1 to 7 are the implementation, and every detail in them exists to make section 8's arithmetic come out favourably. Sections 9 and 10 are the attacks that the implementation cannot reach. Sections 11 to 13 are infrastructure and operations.

The one idea to keep. An OTP proves that someone currently controls a delivery channel. It does not prove who they are, and it does not prove who they are talking to. Every limitation in this document — SIM swap, SS7, relay phishing — is a restatement of that single sentence. Build it as well as it can be built, and know what it is still not doing.
