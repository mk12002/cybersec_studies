01 — Vocabulary

Terminology, precisely

These terms are conflated constantly, including in vendor documentation, and the conflation hides real security differences.

FIDO2The umbrella: WebAuthn (W3C) plus CTAP2 (FIDO Alliance). Not a protocol you implement directly.
WebAuthnThe browser JavaScript API and the server-side protocol. This is what you write code against.
CTAP2How the browser talks to the authenticator over USB HID, NFC or Bluetooth. Relevant when the authenticator is a separate device.
PasskeyA FIDO2 credential that syncs across devices. Passkeys are WebAuthn credentials; the word is a UX label for the synced variety. this distinction has security consequences — see section 7
AuthenticatorWhatever holds the private key. Platform: phone biometrics, Windows Hello. Roaming: YubiKey, Titan.
Relying Party (RP)Your server. It stores public keys and validates assertions.
RPIDA domain name that scopes the credential. The origin check is performed against this, and it is why phishing fails.
AAGUID16 bytes identifying the authenticator model, not the individual unit. Looked up in the FIDO Metadata Service.
02 — Ceremony

Registration

const credential = await navigator.credentials.create({ publicKey: {
  challenge: <32 random bytes from YOUR server>,
  rp:   { name: "Example Bank", id: "bank.example.com" },     # the RPID scopes everything
  user: { id: <opaque handle, NOT the username>,
          name: "alice@example.com", displayName: "Alice Smith" },
  pubKeyCredParams: [ { type:"public-key", alg: -7 },          # ES256 — P-256 + SHA-256
                      { type:"public-key", alg: -257 } ],       # RS256 fallback
  authenticatorSelection: {
    authenticatorAttachment: "platform",   # or "cross-platform" for a hardware key
    userVerification: "required",        # biometric or PIN, not just a touch
    residentKey: "required"                # discoverable — enables username-less login
  },
  attestation: "direct",                   # ask for the hardware's certificate chain
  timeout: 60000,
  excludeCredentials: [ …already registered… ]   # prevents silent duplicate enrolment
}});
user.id must be opaqueIt becomes a permanent identifier visible in the authenticator's UI on some platforms. Use a random handle, never the email address, or you have published PII into the user's device list.
userVerification: requiredForces the UV flag. Without it a credential can be asserted with mere presence — a touch — which is one factor, not two.
residentKey: requiredStores the credential on the authenticator so the user can sign in without typing a username. This is what makes it feel like a passkey.
excludeCredentialsOmitting it lets the same authenticator register twice, which produces confusing duplicates and hides an attacker's enrolment among the user's own.
# what the authenticator builds and signs
authenticatorData =
  rpIdHash    [32]   SHA-256("bank.example.com")
  flags        [1]   UP=1 present · UV=1 verified · AT=1 attested data follows
  signCount    [4]
  aaguid      [16]   which MODEL of authenticator
  credIdLen    [2]
  credentialId [n]   random, 16–64 bytes
  publicKey  [CBOR]  the COSE-encoded P-256 public key

clientDataJSON = {"type":"webauthn.create","challenge":"…",
                  "origin":"https://bank.example.com","crossOrigin":false}

signature = ECDSA_P256_Sign(privKey, SHA256( authenticatorData ‖ SHA256(clientDataJSON) ))
What the server stores, and what it does not

Stores: credential id, the public key, signCount, the RPID, the user handle, and optionally the attestation result.

Does not store: a private key, a password hash, a shared secret, or any biometric data. A full database dump of a passkey-only service yields nothing an attacker can authenticate with. That is a categorical difference from every credential system that preceded it.

05 — Server

Server validation

WebAuthn has no revocation list

There is no equivalent of a certificate revocation list. You cannot tell an authenticator to stop using a key. If a hardware key is stolen, the private key on it remains cryptographically valid forever.

The only revocation is server-side: delete the credential record, and subsequent assertions fail with an unknown credential id. Which means deleting a passkey must also revoke every session that was established with it, or the attacker keeps the access they already have.

06 — The property

Why phishing fails

Adversary-in-the-middle proxies — Evilginx2, Modlishka, Muraena — defeat passwords plus TOTP completely and at scale. Against WebAuthn they fail for a reason that is not a policy choice or a heuristic.

Why this matters for step-up and privileged access

Because re-authentication is a two-second biometric rather than a code to read and type, you can demand it far more often. That turns WebAuthn into a practical basis for just-in-time privileged access: a stale eight-hour session is fine for reading, and any irreversible operation triggers a fresh assertion.

Contrast with a TOTP step-up, which an AiTM proxy relays as easily as the initial login. A privileged access system gated on TOTP is gated on something phishable; gated on WebAuthn it is not.

08 — Attestation

Attestation

Attestation answers a question ordinary registration does not: what hardware generated this key?

FIDO Alliance root
   └─ vendor CA (Yubico, Apple, Microsoft)
        └─ per-MODEL attestation certificate     # batched — same cert for every unit
             └─ signs the attestation statement at registration

# the model identifier travels in authenticatorData
AAGUID  2fc0579f-8113-47ea-b116-bb5a8db9202a   →  YubiKey 5 Series
        d8522d9f-575b-4866-88a9-ba99fa02f35b   →  Apple passkeys
# resolved against the FIDO Metadata Service at https://mds.fidoalliance.org/
Verify the chainAttestation format (packed, tpm, android-key, none), certificate chain to a trusted root, and the statement signature over authenticatorData.
Then apply policyAn allowlist of AAGUIDs, a minimum FIDO certification level, and a rule on whether none attestation is acceptable.
Certificates are per-model, not per-unitDeliberately, for privacy: attestation must not become a tracking identifier. You learn the model, never the individual device.
The supply-chain caseWithout attestation verification, a counterfeit "security key" with an exportable software key is indistinguishable from a real one. This is the concrete reason enterprises verify it.
Attestation has a real cost

An AAGUID allowlist rejects every authenticator you have not explicitly approved, including new models released after your list was written and consumer devices your employees actually own. That is correct for a high-assurance enterprise deployment and wrong for a consumer product, where it converts into a support ticket and a user who gives up and uses the password path.

09 — Residual risk

What still breaks

WebAuthn secures the authentication event. Three things around it remain exactly as vulnerable as they always were.

Pass-the-cookie

WebAuthn proves:  "the holder of this passkey authenticated, just now, on this origin"
the session is:   a long-lived bearer token that represents that event

# XSS, a malicious extension, or malware reading the browser's cookie database
# all yield the same thing: a cookie that works from anywhere.
The passkey is never needed again.
Layered, because none of these is sufficient alone
  • HttpOnly blocks the XSS read path. SameSite=Strict blocks CSRF. Secure blocks the network path.
  • Short sessions, so a stolen cookie expires quickly.
  • IP or device binding, which raises the bar and breaks mobile users — soft-bind and alert rather than hard-fail.
  • Step-up on sensitive operations, which is the one that genuinely helps: a stolen cookie cannot approve a payment or delete a user without a fresh assertion.
  • Token Binding (RFC 8471) would have solved this cryptographically. Browsers removed support in 2021. DPoP (RFC 9449) is the application-layer successor and is gaining traction.

Downgrade to the legacy path

the service supports passkeys AND password + TOTP  (i.e. it is mid-migration)

1. the phishing proxy detects a WebAuthn challenge in the response
2. it strips the challenge and injects a password prompt instead
3. the user sees a password form. They have a password. They type it.
4. the proxy relays password and TOTP in real time → classic AiTM succeeds

# fix: allow_password_auth = false per account, enforced server-side.
# if the server will not accept a password, the proxy has nothing to offer.

Detection is easy and worth wiring up: a legacy authentication attempt on an account that has passkeys registered has no benign explanation in a mature deployment. Alert on it.

Recovery — the weakest link, essentially always

1. "I lost my device"  →  send a recovery email
2. attacker who controls the victim's inbox clicks the link
3. the recovery page lets them register a NEW passkey — theirs
4. full account access, without ever touching the victim's authenticator

# WebAuthn on the front door is theatre if the back door is an email link.
# the attacker attacks the weaker credential, which is what attackers do.

11 — Failure modes

The recovery paradox

Strong authentication needs a recovery path. Any recovery path that works when you have genuinely lost your device also works for an attacker who compromised whatever it depends on. There is no solution, only a choice of trade.

OptionSecurityHow it fails
No recoverymaximumLose every authenticator and the account is gone permanently. Used for root keys and cold storage. Guarantees a support cost.
Backup codeshigh128-bit, one-time, offline. Fails when the user stores them in the password manager that was already compromised — or loses them.
Multiple passkeyshighrecommended for enterprise Require two before enabling passkey-only. Fails only if all devices are lost together.
Trusted contactsmediumM-of-N approval. An attacker must compromise several independent people. Fails to collusion.
Delayed recoverymediumA three-day wait with notification on every channel, so the real owner can cancel. Fails when the owner is unreachable for three days.
A workable enterprise split

Tier 1 — executives, engineers, anyone with production access. Two or more hardware keys, no self-service recovery at all. Recovery is an IT-verified identity check plus an approval workflow, logged and alerted.

Tier 2 — everyone else. Platform passkeys plus backup codes, with self-service recovery gated behind a 24-hour delay and notification on every registered channel.

The important part is that Tier 1 recovery is a human process, not an endpoint. Any endpoint that can re-enroll an authenticator is an endpoint an attacker can reach.

Cross-device reality, which drives users back to passwords

Apple passkeys sync across an Apple ID and are not natively available on Android or Chrome for Windows. Google's sync covers Android and Chrome. Windows Hello is TPM-bound and does not sync by default. Crossing ecosystems means a QR code and Bluetooth proximity, which works and is slow and fails on kiosks and shared machines.

Two failure modes follow. A user at a shared device falls back to the password path, which is exactly the downgrade risk from section 9. And corporate MDM that blocks iCloud Keychain produces passkeys on the phone that never reach the laptop. For shared-device and cross-ecosystem scenarios, issue hardware keys rather than hoping proximity works.

Drills

  1. Run the phishing proxy. Stand up a reverse proxy on a different hostname pointed at your staging login, and confirm the WebAuthn assertion is rejected while password plus TOTP sails through. Nothing teaches the property faster.
  2. Replay a challenge. Capture a valid assertion and submit it twice. The second must fail. Then check whether you mark the challenge used before verification.
  3. Test the downgrade path. Strip the WebAuthn challenge from a response and offer a password form. If the server accepts the password for an account with passkeys, you have the gap.
  4. Attack your own recovery. With access to a test user's email, how many steps does it take to register a new passkey? That number is your real security level.
  5. Delete a passkey and confirm the sessions created with it are revoked. If the old session still works, the credential deletion did nothing to an attacker already inside.
  6. Check the signCount handling. Submit an assertion with a counter lower than stored. Confirm you flag it, and confirm you do not flag the 0/0 case for synced passkeys.
  7. Try a shared device. Attempt cross-ecosystem login on a machine that is not yours, and time it. Whatever happens is what your users will do, including giving up.
  8. Steal your own cookie. Copy a session cookie into another browser and confirm what you can do with it. Then add step-up on the sensitive operations and re-run.

How to use this. Sections 1 to 5 are the mechanism and the code you write. Section 6 is the reason to bother. Sections 7 and 8 are the deployment choices that change the threat model. Sections 9 to 12 are everything the cryptography does not cover, which is where your incidents will actually come from.

The one idea to keep. WebAuthn makes the authentication event unphishable and does nothing for the session it produces or the recovery flow that bypasses it. Deploying passkeys without fixing recovery moves the attack rather than stopping it. Audit the recovery path first, and the cryptography last.
