01 — Narrative

The flow, narrated

The relying party has registered with Google, holds a client ID and secret, and has pre-registered its exact redirect URI. Everything below follows from that registration.

  • T+0The button Nothing has gone over the wire. The frontend builds an authorization URL client-side and navigates to it. Before it does, the backend generates and stores two secrets: a state value of at least 128 random bits, and a PKCE code_verifier of 256 bits. Only the SHA-256 of the verifier travels to Google.
  • T+50–300 msGoogle validates the request Client ID exists. Redirect URI matches a registered value by exact string comparison, not a prefix. Scopes are valid. Response type is permitted. If a Google session cookie is present the login form is skipped.
  • T+1–30 sThe user authenticates and consents Credentials are entered on Google's origin. The relying party never sees them, which is the point. Password hashing, 2FA, risk scoring and device trust all happen opaquely inside Google.
  • T+3 sThe authorization code Google mints an opaque random code with a 60-second TTL, single use, bound to the client ID, the redirect URI, the user identity, the approved scopes and the PKCE challenge. It arrives at the callback in a query string, which is safe precisely because of those bindings.
  • T+3.1 sThe callback Validate state against the session before doing anything expensive. Then extract the code. State validation is pure local logic and costs nothing, which matters when the endpoint is being flooded.
  • T+3.1–3.3 sToken exchange, server to server A POST from the backend to Google's token endpoint carrying the code, the client secret and the PKCE verifier. Google checks all five: code unused and unexpired, client matches, redirect URI matches exactly, secret authenticates, and SHA-256 of the verifier equals the stored challenge.
  • T+3.4 sSession established Verify the ID token signature and claims. Look the user up by sub, never by email. Create a fresh session, set the cookie, redirect. The user experienced one button and a familiar screen.
Why not just return the token to the browser?

That was the implicit flow and it is deprecated. A token delivered in a URL fragment appears in browser history, in the Referer header, and in every server access log along the path, and it is long-lived. An authorization code in the same place is 60 seconds old, usable once, and worthless without a secret the browser never holds. The code is a claim ticket, not the goods.

02 — Model

The three tokens

Google returns three things at once and they are routinely confused. They answer three different questions and have three different lifetimes.

The refresh token is the crown jewel

It outlives password changes at your app, it works from anywhere, and it grants continuing access to the user's Google data. Store it AES-256-GCM encrypted with a key in KMS, keep a SHA-256 of the plaintext as the lookup index, and make sure the database credentials do not also grant KMS access. That IAM separation is the control: a full database dump then yields ciphertext and nothing else.

03 — Protocol

The authorization request

https://accounts.google.com/o/oauth2/v2/auth
  ?response_type=code
  &client_id=<RP_CLIENT_ID>
  &redirect_uri=https://app.example.com/auth/callback
  &scope=openid%20email%20profile
  &state=<128-bit CSPRNG>                 # CSRF defence — YOU generate and validate this
  &code_challenge=<base64url(SHA256(verifier))>
  &code_challenge_method=S256                # "plain" is deprecated and rejected
  &nonce=<random>                          # replay defence for the id_token
  &access_type=offline &prompt=consent       # only if you actually need a refresh token
stateOpaque to Google, which simply echoes it. Generated by you, stored server-side in the session, compared on callback with a constant-time comparison. Without it the callback is an unauthenticated endpoint that accepts any code.
code_challengeThe SHA-256 of a per-flow secret. Proves the party exchanging the code is the same party that started the flow. Mandatory for public clients, strongly recommended for everyone.
nonceEchoed into the id_token. Validating it prevents an old, still-valid ID token from being replayed into a fresh flow.
redirect_uriCompared by Google using exact string matching. RFC 6749 requires this. Prefix or wildcard matching is a known mis-implementation that turns any open redirect into code theft.
access_type=offlineThe only reason a refresh token is issued. If you do not call Google APIs on the user's behalf, omit it and you never hold the most dangerous token.
Where the verifier is stored matters

The code_verifier belongs in the server-side session. Putting it in sessionStorage puts it within reach of any XSS on your origin, which defeats the mechanism it was added to provide. For a pure SPA with no backend the tradeoff is unavoidable, which is one of several reasons a backend-for-frontend pattern is preferred for OAuth.

&code_verifier=dBjftJeZ4CVP…

# Google's five checks, all of which must pass:
1. code exists, unused, unexpired
2. client_id matches the client the code was bound to
3. redirect_uri matches EXACTLY — a trailing slash difference fails
4. client_secret authenticates the client
5. SHA256(code_verifier) == stored code_challenge
Why the redirect URI is sent again when no redirect happens

It is a verification parameter, not a functional one. Because the code is bound to the URI it was delivered to, and that URI must be presented again at exchange, possession of the code is tied to having received it at the legitimate path. An attacker who intercepted a code destined for a different URI cannot exchange it by claiming any URI they like. Mismatch returns redirect_uri_mismatch.

# JIT provisioning must be idempotent — two simultaneous first logins are normal
INSERT INTO users (google_sub, email) VALUES ($1, $2)
  ON CONFLICT (google_sub) DO UPDATE SET email = EXCLUDED.email
  RETURNING id;
CREATE TABLE oauth_refresh_tokens (
  user_id         UUID REFERENCES users(id),
  token_encrypted BYTEA NOT NULL,        # AES-256-GCM, key in KMS
  token_hash      VARCHAR(64) NOT NULL,  # SHA-256 of plaintext, for lookup only
  scope           TEXT NOT NULL,
  issued_at       TIMESTAMPTZ NOT NULL,
  revoked_at      TIMESTAMPTZ,
  UNIQUE(token_hash)
);
What runs asynchronously, and why it must

The callback is on the user's critical path, so only authentication belongs there. Audit events, first-login emails, enterprise group provisioning and analytics all go to a queue. A user should never wait on an SMTP handshake to finish logging in, and an email service outage should never break authentication.

Never cache the callback

If a CDN caches a response from /auth/callback it will serve one user's Set-Cookie to the next visitor, logging them in as somebody else. This is a total multi-tenant session bleed from a single caching rule.

Four independent controls, because one will be misconfigured: send Cache-Control: no-store, no-cache, private on every auth response; configure the CDN to pass through /auth/* unconditionally; configure it never to cache any response carrying Set-Cookie; and test it by logging in, then hitting the same path from a clean browser.

08 — Offence

State, CSRF and session fixation

CSRF on the callback — login as the attacker

Session fixation

1. attacker plants a known cookie in the victim's browser
   (subdomain cookie injection, XSS on any subdomain, or shared device)
       session_id = attacker_known_value

2. victim completes the OAuth flow normally

3. the RP reuses the existing session to store state, and never rotates it

4. the RP binds the authenticated user to attacker_known_value
   → the attacker's browser, holding the same cookie, is now the victim

# THE FIX: generate a NEW session id on successful authentication,
# even though you needed a pre-auth session to hold `state`.
Why SameSite=Strict breaks this flow

Strict means the cookie is never sent on a cross-site request, including top-level navigations. Google's redirect to your callback is exactly that. With Strict, the session cookie holding your state value is not sent, so you cannot validate state at all.

Lax permits cookies on cross-site top-level navigations that use safe methods, which is a redirect-driven GET. That is why SameSite=Lax is the correct setting here, and why choosing Strict "to be safer" produces a login page that mysteriously loops.

If you genuinely need Strict: make the callback stateless with respect to the cookie by carrying an HMAC-signed, encrypted state value returned by Google rather than a session lookup.

09 — Defence

PKCE and code interception

The code travels in a URL, so it lands in browser history, in your own access logs, and in a Referer header if the callback page links anywhere external. PKCE makes all of that harmless.

Keep codes out of your logs anyway

Strip query parameters from access-log URLs on auth paths, or log only the path. A code in a log is a 60-second window; a code in a log that gets shipped to a third-party log aggregator with a longer retention is a much wider one. The same applies to the Referer header, which will contain accounts.google.com and may carry parameters from Google's own page.

10 — Offence

Token theft and forgery

Algorithm confusion on the ID token

# variant A — the historical one
header  {"alg":"none","typ":"JWT"}
payload {"iss":"https://accounts.google.com","aud":"<RP_CLIENT_ID>",
         "sub":"victim_sub","email":"victim@gmail.com","exp":<future>}
token   header.payload.(empty signature)

# variant B — the live one
Google signs with RS256. The PUBLIC key is published at the JWKS endpoint.
Attacker sets alg=HS256 and computes an HMAC using the public key bytes as the secret.
A library that takes the algorithm from the header will verify it successfully.

jwt.verify(token, key, { algorithms: ['RS256'] });   # the whole fix

Neither variant produces any traffic to Google, so detection has to happen at your service. Log the alg of every inbound token and alert on anything that is not RS256. The expected rate of that alert is exactly zero, which makes it one of the highest-signal detections available.

Open redirect leading to code and token leakage

# requires TWO mistakes, which is why it survives review
1. redirect_uri matched by PREFIX instead of exact string
2. a post-login "next" parameter that is not validated

redirect_uri = https://app.example.com/auth/callback?next=https://attacker.com
→ code delivered to the real callback
→ RP exchanges it legitimately
→ RP then redirects the user to `next`
→ anything in the fragment or URL at that point leaves your origin

Refresh token compromise

Responding to a suspected refresh token compromise
  1. Revoke every stored refresh token for affected users at oauth2.googleapis.com/revoke.
  2. Invalidate all active sessions for those users in Redis.
  3. Delete the stored tokens rather than marking them revoked, so a second dump yields nothing.
  4. Force re-authentication on the next request.
  5. If the scope is a full database dump, rotate the client secret and require everyone to re-authenticate.
  6. Notify affected users with specific guidance, including how to review third-party access in their Google account.
  7. Determine the ingress: database breach, memory dump, or log leak. The answer changes what else is compromised.
Frontend supply chain

A compromised npm package in your build cannot read an HttpOnly session cookie, which is exactly why you use one. It can read the authorization code out of the URL before your code runs, intercept fetch, inject a phishing form, and read anything in localStorage.

Controls: subresource integrity on CDN-loaded scripts, a CSP that constrains where data can be sent, a lock file with pinned versions, and never putting tokens in localStorage.

11 — Failure modes

Failure modes

JWKS cache stampede

Google rotates keys every few weeks. If every instance caches JWKS in-process with the same TTL, they all expire together and all fetch at once. Google rate-limits the fetch, and ID token validation fails everywhere simultaneously.

Fix: jitter the cache TTL; use a shared Redis cache with single-flight refresh; negative caching so a refresh cannot repeat within five minutes.

Callback flood

An attacker posts garbage codes to /auth/callback. If you exchange before validating state, every forged request costs you an outbound call to Google — an amplifier you built.

Fix: validate state first, since it is free, and rate-limit the callback by IP at roughly ten requests per minute.

The 500 between exchange and session write

Where the failure happened determines the recovery. Before the exchange: the code is still valid at Google and the user can simply retry. After the exchange, before the session write: the code is consumed, tokens exist at Google that you did not store, and retrying the exchange with the same code returns invalid_grant. Your handler must detect that error and restart the flow rather than surfacing it, or the user sees a login that fails forever on refresh.

13 — Scaling

Scaling and drills

Google's token endpointRate-limited per client ID and impossible to parallelise within one login. A marketing email that lands at 09:00 produces a thundering herd. Exponential backoff with jitter, and separate client IDs per product line so each gets its own quota.
Redis sessionsEvery authenticated request is a Redis read. Vertical first, since it is simpler; Redis Cluster when a single node's RAM or operations ceiling is reached; Sentinel for HA without sharding.
JWKS cacheCentralise it in Redis with single-flight refresh so 100 instances produce one fetch, not 100.
User lookupAn indexed read on google_sub, so replicas handle it easily. New-user inserts go to the primary. Route the first read after signup to the primary to avoid read-your-writes surprises.
Auth serviceStateless, so it scales horizontally without limit. Autoscale on latency as well as CPU, because a slow token exchange is not CPU-bound and CPU-only scaling will miss it.
Consistency, where it actually bites

Session creation is forgiving: the first request after login hits the same node by consistent hashing, and replication lag is measured in microseconds. Session deletion is not. A logout that has not replicated leaves a window where the deleted session still validates on another node. If that window matters to you, use synchronous replication for session deletes and accept the latency, or maintain a short-lived revocation set that is checked alongside the session.

Drills

  1. Break state. Comment out the state check in a staging build and execute the login CSRF from section 8 against yourself. Then restore it and confirm the rejection.
  2. Forge an ID token. Take a real one, switch alg to none, strip the signature, and present it. Then try the HS256 variant using the public key from the JWKS endpoint as the HMAC secret. Both must fail.
  3. Test fixation. Set a session cookie manually, log in, and check whether the cookie value changed. If it did not, you have the bug.
  4. Replay a code. Exchange one twice and observe invalid_grant. Confirm your handler restarts the flow rather than showing an error page.
  5. Simulate key rotation. Point at a JWKS with an unknown kid and verify you refresh once and retry once, rather than refreshing on every request.
  6. Prove the CDN passthrough. Log in, then request the callback path from a clean browser and confirm you are not handed somebody else's session.
  7. Grep your logs for code=, Bearer, refresh_token and raw session identifiers. Anything you find is a finding.
  8. Audit the redirect URI registration in Google Cloud Console for wildcards or prefixes, and audit every post-login next parameter for validation.

How to use this. Sections 1 to 5 are the protocol and every parameter's reason for existing. Section 6 and 7 are your side of the boundary. Sections 8 to 10 are the attacks, which almost all land on the parts you implemented rather than on the parts Google did. Sections 11 to 13 are operations.

The one idea to keep. OAuth's design puts the code in the browser and the tokens on a channel the browser cannot reach. Nearly every serious failure in this document is a case of something crossing back the other way: a token in localStorage, a verifier in sessionStorage, a code in a log, a secret in an image. Keep the two channels separate and most of the attack surface simply is not there.
